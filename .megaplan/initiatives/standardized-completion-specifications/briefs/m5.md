# M5 — Public Extraction and Second Consumer

## Outcome

Extract the proven completion model into a product-neutral Arnold surface,
exercise it through an unrelated non-Megaplan consumer with different domain
obligations and topology, then certify only the behavior that both consumers
actually prove.

## Scope

### In

- Extract neutral schema/types, compiler/admission hooks, verifier/evidence
  registration, composition, inspection, test-harness, and compatibility APIs.
- Keep Megaplan task semantics, prompts, critique policy, phase names, and
  product defaults in Megaplan.
- Build an unrelated consumer without importing or copying Megaplan code,
  adapters, defaults, fixtures, or terminology.
- Require different business obligations, at least one human or effect
  boundary, rework/new-task admission, and a nontrivial composition shape.
- Prove clean-checkout and independently installed package use, not only source
  checkout imports.
- Exercise new-instance compatibility, pinned old-run resume, incompatible
  change rejection, explicit migration/quarantine, verifier independence, and
  schema evolution.
- Publish generated reference docs and minimal author examples.
- Freeze the initial stable compatibility promise only after adversarial
  comparison and removal of product leakage.

### Out

- Generalizing arbitrary Megaplan phases.
- Manufacturing a toy consumer that mirrors Megaplan.
- Promising unsupported aggregation or migration semantics.
- Replacing existing authority/evidence subsystems with a cleaner-looking API.

## Locked Decisions

- The public standard contains completion semantics, not product policy.
- A second consumer is evidence, not ceremony; it may force revision or removal
  of candidate abstractions.
- Stability follows substitutability proof.
- Existing Megaplan behavior remains a first-consumer conformance suite.

## Open Questions

- Which existing unrelated Arnold workflow provides the strongest adversarial
  shape without creating a new product project?
- Which interfaces remain experimental because only one consumer exercises
  them?
- What compatibility matrix is honest for spec, verifier, binding, and
  installed-runtime evolution?

## Constraints

- Target no more than two weeks.
- The second consumer must be machine-scanned for Megaplan reverse imports and
  copied product adapters.
- Test source, editable install, wheel/sdist, and supported cloud worker paths.
- Stable publication requires current content-addressed proof from both
  consumers.

## Touchpoints

- neutral Arnold workflow/completion packages
- package exports and compatibility/versioning policy
- verifier/evidence-provider registry
- local test harness and generated reference documentation
- selected unrelated consumer
- Megaplan adapter and conformance suite

## Done Criteria

- The unrelated consumer declares small domain obligations while standard
  obligations and composition are generated.
- Both consumers use the same neutral implementation and independently bound
  product semantics.
- Static and runtime checks prove no Megaplan dependency or copied policy in
  the unrelated consumer.
- Clean install, resume, migration/quarantine, rework, human/effect boundary,
  absence proof, waiver taint, and changed-runtime rejection scenarios pass.
- The compatibility/evolution policy identifies stable, experimental,
  deprecated, and tombstoned surfaces.
- Public documentation shows authoring, generated inspection, human
  verification, and causal failure diagnosis.
- A final conformance report maps every North Star completion claim to exact
  proof artifacts and leaves unproven behavior explicitly experimental.

## Anti-Scope

Do not weaken semantics to make the second consumer pass and do not certify an
API solely because it is importable outside Megaplan.
