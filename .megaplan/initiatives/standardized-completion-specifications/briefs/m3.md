# M3 — Megaplan Vertical Slice and Rework

## Outcome

Make one complete Megaplan path authoritative under standardized completion:

```text
finalize/admit
  -> execute
  -> landed-write and validation evidence
  -> verdict/acceptance
  -> review
  -> reopen existing or admit new rework
  -> execute
  -> workflow aggregate
```

The mandatory captured M10/M11 fixture must pass end to end: legacy `done`
cannot override rejected authority evidence, and a global review finding cannot
enter execution as pseudo-task `REVIEW`.

## Scope

### In

- Compile dynamic task objectives, success criteria, claimed write sets, tests,
  sense checks, and validation jobs into proposed task completion specs.
- Deterministically augment them with landed-write, validation, evidence
  freshness, runtime attestation, custody, authority, and contract-hash
  obligations.
- Reject vague, circular, trivially satisfied, unscoped, or unverifiable
  model-proposed obligations at admission.
- Bind and execute the selected task slice through the existing executable
  frontier and evidence producers.
- Make `accepted(...)` a candidate disposition only; accept it only through the
  M2 evaluator and existing transaction.
- Route review findings by identity:
  - reopen an existing task under a new attempt/generation binding;
  - propose and normally admit a genuinely new task with a new stable ID; or
  - record justified non-action under an explicit review disposition that
    cannot masquerade as task completion.
- Preserve accepted evidence for unaffected tasks during rework.
- Aggregate the slice only after every admitted binding has an accepted or
  explicitly permitted disposition.
- Add causal status explaining the exact failed obligation and repair frontier.

### Out

- No migration of every Megaplan workflow phase.
- No stable public Arnold API.
- No broad workflow composition beyond the path needed for the slice.

## Locked Decisions

- New review work returns through normal finalization/admission.
- `REVIEW` is a review-scope label, never an executable task identity.
- Validation jobs are deterministic admitted obligations, not advisory prose.
- Review cannot directly mutate completion state.
- Existing task semantic identity may persist across rework, but the binding
  and attempt/generation must change.

## Open Questions

- What exact task/finding identity mapping preserves legacy review artifacts
  while preventing pseudo-task execution?
- Which narrow enablement boundary gives a safe, reversible first cutover?
- Which current status surfaces require projection updates so operators see the
  bound verdict rather than legacy task status?

## Constraints

- Target no more than two weeks.
- The cutover must be fail-closed, scoped, and reversible without dual writers.
- Reuse current executor, validation runner, evidence providers, stores, and
  acceptance transaction.
- Keep accepted unrelated task evidence immutable.
- Include crash/retry/reentry tests at each durable boundary in the slice.

## Touchpoints

- Megaplan finalize/admission handlers
- execution task dispatch and validation jobs
- completion and review evidence orchestration
- review/rework planning and task identity
- status projections and causal diagnostics
- M10/M11 golden trace fixture

## Done Criteria

- The full slice completes under one binding per durable subject.
- Legacy `done` with `accepted=false` or `no_accepted_attempt` remains
  unsatisfied.
- A new review finding becomes an admitted executable task; an existing finding
  reopens the intended task; `REVIEW` never reaches the executor.
- Accepted evidence for unrelated tasks survives rework without rebinding.
- A crash at admission, execution, review, or rework resumes from pinned
  identity without duplicate effects or duplicate task admission.
- Operator status names the current binding, candidate disposition, failed
  obligation, admissible evidence, and next repairable action.
- M3 publishes the executed golden trace and migration inventory for M4.

## Anti-Scope

Do not bypass admission to “get rework moving,” and do not retain a legacy
status field as a competing terminal authority.
