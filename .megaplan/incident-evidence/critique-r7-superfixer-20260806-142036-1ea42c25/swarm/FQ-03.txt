## question_id
FQ-03 — "Which fields besides `depends_on` and `dependency_reasons` carry task identities through finalize?"

## verdict
**Six additional structured fields carry task identities through finalize.** Two are model-emitted in the raw candidate (`sense_checks[].task_id`, `critique_resolution_coverage[].task_ids`); four are handler-generated/derived inside `_write_finalize_artifacts` (`validation.plan_steps_covered[].finalize_item_ids`, `validation.orphan_tasks`, `validation_jobs[].task_id`/`scope`/`evidence_label`/`reason`, and schema-defined `user_actions[].blocks_task_ids` — empty here). **`watch_items` and `meta_commentary` carry no structured task identity (prose only).** The splitter (`split_high_complexity_tasks`/`split_task`) rewires **none** of them: it replaces 6 parent tasks (T1–T5, T7) with 12 `_impl`/`_proof` subtasks in `payload["tasks"]` only, leaving `depends_on`/`dependency_reasons` dangling (the blocker), and also leaving **6 stale `sense_checks[].task_id` refs (SC1,SC2,SC3,SC4,SC5,SC7), 55 stale `critique_resolution_coverage[].task_ids` entries, and pre-split-generated `finalize_item_ids`** in the payload that would be published on a fixed path. `validation_jobs` are compiled **after** the split and therefore already carry post-split ids — they need no transformation, only the existing ordering invariant (split → compile jobs → feasibility). `graph_admission.py` and `execution_evidence.py` consume task identities only as byte-digests or via `tasks[].id`/`sense_checks[].id`, never via the stale-able fields.

## structure_classification
Root cause is a **structural identity-integrity defect (single-transform, multi-consumer)**: one mutator (`split_high_complexity_tasks`) rewrites the identity set of one container (`tasks`) while five sibling structured consumers (`depends_on`/`dependency_reasons`, `sense_checks[].task_id`, `critique_resolution_coverage[].task_ids`, `validation.plan_steps_covered[].finalize_item_ids`, `validation.orphan_tasks`) are keyed on the pre-mutation identity set and are never re-keyed. The hard failure is gated only at the `depends_on` consumer; the other four fail **silently** (no existence validation anywhere: feasibility checks only deps; semantic postcheck checks only U-prefixed ids; custody digests bind bytes without validating existence; execution filters sense checks by task_id at batch time). `validation_jobs` is structurally immune (derived post-mutation). `watch_items`/`meta_commentary` are prose, structurally immune.

## immediate_decision_informed
Yes — the pending Sol repair ("rewire dependents after split, or map removed parent ids → impl/proof") must **not stop at `depends_on`/`dependency_reasons`**. The same post-split transformation policy is required for: `sense_checks[].task_id` (6 stale: SC1–SC5, SC7), `critique_resolution_coverage[].task_ids` (55 stale entries), and `validation.plan_steps_covered[].finalize_item_ids` + `orphan_tasks` (regenerate or re-key after split; `_reconcile_validation_after_mutation` is insufficient — it only adds orphans). Otherwise a repaired candidate passes feasibility but publishes a contract whose sense checks never fire for split tasks, whose critique-coverage digest binds removed-parent ids, and whose validation block claims non-existent tasks. `validation_jobs` and `watch_items` need no transformation.

## durable_decision_informed
Yes — three durable engineering conclusions: (1) introduce a single post-split identity-rewrite pass with an explicit parent→impl/proof mapping table, applied uniformly to `depends_on`/`dependency_reasons`, `sense_checks[].task_id`, `critique_resolution_coverage[].task_ids`, and `validation` (recompute `finalize_item_ids` and `orphan_tasks` after rewiring); (2) preserve the ordering invariant split → rewire → `compile_validation_jobs` → `compile_task_feasibility` (jobs are already last-compiled, which is why they self-heal); (3) add an existence cross-check (all task-id references in `sense_checks`, `critique_resolution_coverage`, `validation.plan_steps_covered[].finalize_item_ids`, `orphan_tasks` ⊆ `tasks[].id`) inside `compile_task_feasibility` or `_finalize_semantic_postcheck`, so silent staleness in any consumer becomes a deterministic rejection instead of a silent contract drift. Also note T10/T13/T16's `split_mutating_validation` non-splits mean their (legitimately dangling post-rewire) deps must map onto the split parents' impl subtasks, not the removed parents, for the rewrite table to be complete.
