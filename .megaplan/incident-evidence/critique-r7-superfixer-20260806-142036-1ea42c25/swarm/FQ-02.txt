**confidence:** High. Verdict is derivable purely from the splitter's own graph (`proof.depends_on=[impl]`, `consumes_output`), the scheduler's dependency-satisfaction gate, the terminal-status/completion contract, and a direct in-memory demo on the bound engine; existing tests contain no contradicting assertion (they only assert the impl→proof edge, which is consistent).

**structure_classification:** Deterministic task-graph contract semantics (split-parent substitution + topological scheduling + authority-corroborated completion). Root cause of the incident is the missing dependent-rewire step in `split_high_complexity_tasks`; FQ-02 resolves the design judgement of which target that step must use.

**immediate_decision_informed:** The minimal fix should rewrite every dependent's `depends_on`/`dependency_reasons` entry that referenced a removed split parent P to **`P_proof`** (preserving `required_output` = P's write_set paths), not `P_impl`. Wiring to `P_impl` would place dependents in the same dispatch batch as `P_proof`, letting them consume unverified output and weakening proof ordering; wiring to `P_proof` transitively enforces impl→proof→dependent.

**durable_decision_informed:** Add a regression assertion that (a) `split_high_complexity_tasks` leaves no dangling references (feasibility admitted), and (b) dependents of a split parent rewire to the `_proof` terminal successor — e.g., in `test_task_splitter.py`, assert `D["depends_on"] == ["T1_proof"]` and `dependency_reasons["T1_proof"]["kind"] == "consumes_output"`, plus an `compute_task_batches` batch-order assertion that D is strictly after `T1_proof`. This preserves the proof-ordering invariant for all future split graphs without weakening it for any dependency kind.
