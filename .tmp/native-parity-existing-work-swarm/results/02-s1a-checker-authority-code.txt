Core scaffolding and data models exist (row IDs, diagnostic codes, boundary vocabulary, checker API). However, three of the five subcomponents are missing or incomplete per the master plan's own SA5/Q3/Q9 findings, which I've verified against code.

### 3. What Can Be Reused or Generalized

- **Checker API and result carrier**: `check_workflow_source(evidence=..., boundary_contracts=..., boundary_evidence=...)` at `source_compiler.py:642-719` is a well-structured entry point; new diagnostic rules can be added as additional `_*_diagnostics()` functions appended to the pipeline at :697-713.
- **Data models**: `SemanticEvidence`, `BoundaryContract`, `BoundaryReceipt`, `SemanticFinding`, and all Stable Row IDs are frozen, sidecar-serializable, and ready for consumption by new prohibited-carrier checks.
- **Boundary contract registry**: `boundary_contracts.py` pattern can be extended for prohibited-carrier whitelist entries (explicit fencing of inert compatibility carriers).
- **Handler semantics data**: `handler_semantics.py:29-54` classification can feed a production carrier scan that distinguishes route-authoritative from descriptive carriers.
- **Carrier table test**: `test_semantics_carrier_table.py` verification logic can be promoted into a production `CarrierScanner` class.

---

### 4. What Still Must Be Built

1. **Prohibited-carrier structural rejection rules**: A new diagnostic module that flags `handler_ref` as route authority, `route_bindings`, component-owned route decisions, manifest/backend route translation, auto next-step derivation, CLI dispatch, and compatibility projection evidence. Must be structural (AST/import-level), not token blacklists.

2. **Carrier scan/classification tier**: A production `CarrierScanner` that distinguishes route-authoritative from descriptive carriers, with a falsifiable tier boundary (master plan :76-79) — random sample + corrupt + prove split-outcome unchanged.

3. **Current-shape negative fixture**: A permanent, CI-pinned fixture mirroring the source ranges at `master-plan.md:427` (`workflow.pypeline:14-34, :81-280, :281-383, :390-540; planning.py:247-268, :583-716; components.py:1154-1781, :2664-2669; _compatibility.py:101-115, :173-207`), pinned to diagnostic codes.

4. **Installed-package checker path**: No strict installed-package checker exists (Q10 at `master-plan.md:235-237`). Must use `importlib.resources` + smoke test against installed artifact.

5. **Row registry centralization**: Row IDs and component-ref-to-row mappings are distributed across `semantic_evidence.py`, `boundary_contracts.py`, and `source_compiler.py`. A single `RowRegistry` class would eliminate drift risk.

---

### 5. Recommended Sprint Plan Adjustment

- **Split S1a** into two deliverables: (a) the existing checker scaffold + row registry + boundary evidence (already done, mark as **S1a-foundation**), and (b) **S1a-prohibited** for the structural prohibited-carrier rules + carrier scan tier + current-shape negative fixture + installed-package smoke.
- **Prioritize current-shape negative fixture first** — it's the highest-leverage anti-false-pass control and is explicitly cited as missing in SA5.
- **Do not treat `handler_semantics.py` as the carrier scanner**. It's classification data, not the tiered scan with falsifiable boundary. Build `CarrierScanner` as a new `arnold/workflow/carrier_scan.py`.
- **Pin the negative fixture to exact diagnostic codes** (AWF200-series for prohibited carriers) so renamed/renamed-encoded carriers trigger the right codes, not just any failure.
