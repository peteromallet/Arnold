### 3. What Can Be Reused or Generalized

1. **`evaluate_no_review_terminal()`** (`execute/policy.py:360-408`) — already a pure function; can be lifted directly into source-native policy without refactoring. Its typed `NoReviewTerminalDecision` return is already clean.

2. **The finalize fallback handler** (`handlers/finalize.py:1500-1582`) — writes correct artifacts (`finalize_revise_feedback.json`, `gate.json`, `gate_carry.json`), correctly routes to revise with `STATE_CRITIQUED`. This mechanism itself doesn't need replacement; the *evidence* that proves the fallback route exists needs to come from source-native constructs instead of `components.py:FINALIZE_POLICY`.

3. **Boundary contracts** (`boundary_contracts.py:551-599`) — well-structured, test-covered, and already referenced by the checker. These remain valid as evidence targets; only the *source of truth* for the route declarations needs to shift.

4. **Semantic health checks** (`semantic_health.py:1347-1510`) — substantial validation of projection/fallback boundaries already exists and can be pointed at source-native declarations once they exist.

5. **Tests** — `test_execute_policy.py` tests for `evaluate_no_review_terminal`, `test_row_evidence_checker.py` has S5 fixture validation, `test_boundary_contracts.py` has contract golden tests. These can be reused as parity/regression gates.

### 4. What Still Must Be Built

1. **Source-native S5 row evidence** — The current `_implemented_s5_boundary_rows` (`source_compiler.py:1783-1874`) gates all three finalize rows (`S5_FINALIZE_ARTIFACTS_ROW_ID`, `S5_FINALIZE_FALLBACK_ROW_ID`, `S5_FINAL_PROJECTION_ROW_ID`) on `isinstance(..., Mapping)` checks against `components.py:FINALIZE_POLICY`. The master plan requires these rows to pass on source constructs in `workflow.pypeline` or named native subworkflows (master plan line 741).

2. **Source-native final projection constructs** — Currently `final_projection_routes` with its four cases (`execute`, `revise_fallback`, `no_review_done`, `no_review_deferred_human`) lives only in `components.py:1477-1504`. These need source-visible equivalents — either explicit projection declarations in `workflow.pypeline` or attached to named policy surfaces free of route-table behavior.

3. **Source-native no-review/deferred-human terminal** — While `evaluate_no_review_terminal()` is already a pure function, the terminal routing (`handlers/execute.py:555-655`) is still handler-level dispatch, not driven by source-native constructs. The `skip_review_routes` in `components.py:1450-1467` also needs source-native equivalents.

4. **Split-outcome scenario tests** as specified in master plan line 742: review pass, review rework, review cap with/without blockers, no-review terminal, deferred-human terminal, finalize fallback revise. Current tests exist for the policy function (`test_execute_policy.py`) but not as full S5 split-outcome scenarios.

### 5. Recommended Adjustment to Sprint Plan

The S5 sprint scope in the master plan (lines 729-762) correctly identifies the gap: "Strict checker must require S5 row evidence; S5 cannot pass on `Mapping` existence in `REVIEW_POLICY` or `FINALIZE_POLICY`." The adjustment should be:

1. **Don't rebuild the behavioral machinery.** The finalize fallback handler, `evaluate_no_review_terminal()`, boundary contracts, and semantic health checks are already solid.

2. **Focus S5 effort on source-native declarations.** The core work is adding explicit finalize/projection constructs to `workflow.pypeline` (or named native subworkflows) that declare: fallback routes (`finalize→revise` on contract failure), terminal projection cases (`execute`, `revise_fallback`, `no_review_done`, `no_review_deferred_human`), and no-review terminal routing (robustness→terminal-outcome mapping).

3. **Update `_implemented_s5_boundary_rows`** (`source_compiler.py:1783-1874`) to require source-native evidence instead of `Mapping` existence on `components.py:FINALIZE_POLICY`.

4. **Add the 7 split-outcome scenarios** from master plan line 742, leveraging existing `evaluate_no_review_terminal` tests as a foundation.

5. **The risk is low** that this breaks anything: the handler/policy machinery is already in place; S5 is about shifting the *evidence authority* from `components.py` policy surfaces to source-native constructs.
