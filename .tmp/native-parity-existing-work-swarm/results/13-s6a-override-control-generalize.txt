## 1. Verdict: Already exists, substantially complete

S6a (Override/Human Control Surface) is **largely built**. All six override actions plus invalid-action rejection exist in production code with handlers, state-machine guards, authority receipts, boundary fixtures, semantic-health tests, auto-driver integration, and a parallel control-interface routing path behind a feature flag. The master plan's S6 sprint is not about building the override surface from scratch — it's about extracting the existing override route authority out of handler code and into source-visible `.pypeline` constructs, removing auto-drive as a second route brain, and quarantining compatibility projections.

| Artifact | Generalization path |
|---|---|
| `OVERRIDE_ACTION_MATRIX` (`override_matrix.py`) | Already a clean declarative registry. The pattern of `family`, `route_signal`, `dispatch_surface`, `control_routed` can be lifted into a shared authority-registry base class for review-gate, tiebreaker, and execute-approval surfaces. |

## 4. What still must be built

Per the master plan (L764–797) and verified gaps:

1. **Source-visible `.pypeline` extraction**: Override actions are currently dispatched through handler functions (`handlers/override.py`). The master plan requires extracting override route authority into named `.pypeline` source constructs. The override matrix already declares `route_signal` and `target_ref` for each action — these declarations must become actual `.pypeline` route nodes, not just metadata.

2. **Collapse the dual-path dispatch**: The `control_interface_routing_on()` feature flag (L1937–1938) gates a parallel strangler path. S6 must collapse this to a single source-authoritative path. The flag is OFF by default — the production path still goes through handler functions.

3. **Remove auto-drive as second route brain**: `auto.py` contains `_override_force_proceed_in_process` (L914), `_override_adopt_execution_in_process` (L939), and escalates independently of the override matrix. S6 must make auto-drive consume the same source-derived override surface.

4. **Quarantine `_compatibility.py` and `route_dispatch.py`**: These still exist and may carry route authority. The master plan (L789) requires they "consume source-derived semantics or be fenced from evidence and runtime route authority."

5. **Dedicated test file**: `test_override_auto_compat_quarantine.py` (referenced in master plan L773) does not exist. No override-specific test file was found in `tests/`.

6. **Split-outcome scenarios not yet verified**: The master plan (L777) lists force-proceed from allowed states, abort, replan, recover-blocked, resume-clarify, adopt-execution, invalid force-proceed state. Semantic health tests exist for authority records but not full split-outcome behavioral tests.

## 5. Recommended adjustment to the native semantic parity sprint plan

**S6 should be reframed from "build override surface" to "extract and collapse existing override surface."** The implementation is not greenfield. Specifically:

- **S6a (this component) is ~80% done.** The risk is not missing functionality — it's that the dual-path dispatch (handler vs. control-interface) and auto-drive's independent override logic create a split-brain that the feature flag was meant to bridge but hasn't been collapsed yet.
- **Priority order**: (1) Write split-outcome behavioral tests first to lock current behavior; (2) collapse the `MEGAPLAN_CONTROL_INTERFACE_ROUTING` flag by making the control-interface path the sole path; (3) make auto-drive consume the same surface; (4) extract override actions from handler functions into `.pypeline` route nodes using the existing `route_signal`/`target_ref` declarations in the override matrix as the target schema; (5) quarantine `_compatibility.py`/`route_dispatch.py`.
- **Risk**: The override matrix's `dispatch_surface` field currently splits actions between `"workflow.route_binding"` (abort, force-proceed, replan) and `"workflow.native_policy"` (adopt-execution, recover-blocked, resume-clarify). This split must be reconciled during extraction — it's not clear whether `"workflow.route_binding"` actions have `.pypeline` carrier equivalents yet.
