## Swarm Audit: S2b Gate/Revise Native Loop

### 1. Verdict: **Partly exists**

The gate/revise handler logic and component policy surfaces are sophisticated and production-grade. However, all route authority, loop control, and semantic decision-making live inside handler-local state mutations and component policy surfaces — not in native `.pypeline` source. No S2b extraction sprint has been executed; the S2 sprint in the master plan (`master-plan.md:618–656`) specifies exactly this extraction scope.

### 3. What Can Be Reused or Generalized

- **`handlers/gate.py` logic**: The 1173-line gate handler is a complete, tested implementation of preflight checks, reprompt, downgrade, debt recording, severity-gated termination, iteration/no-progress cap enforcement, and all route signals. The extraction task is to lift this semantics into native source constructs, not to re-implement it from scratch. The handler can initially serve as the phase body behind a typed native interface.
- **`components.py` policy surfaces**: `GATE_POLICY` and `REVISE_LOOP_POLICY` contain the complete route vocabulary, severity taxonomy, and termination rules. These can be translated into declared policies on native source constructs rather than remaining as opaque component dicts.
- **`native_interfaces.py`**: GATE and REVISE interfaces already define stable IDs, path groups, input/output schemas, and legacy alias mappings — directly usable for typed native phase declarations.
- **`orchestration/gate_checks.py` and `gate_signals.py`**: Preflight and signal logic is well-factored and can be attached as pure phase bodies or invoked from declared policies behind typed interfaces.
- **`workflow.pypeline:390–470`**: The loop shape (`loop(policy=REVISE_LOOP_POLICY)` with `GateOutcome` enum branches) is already in the right form — it just needs the `AUTHORING_GATE`/`AUTHORING_REVISE` calls replaced with native constructs that own their semantics rather than delegating to handlers.
- **Native golden fixtures D3/D4**: Substrate evidence that the native runtime can execute gate-preflight and gate-revise stage sequences. These can be widened as extraction proceeds.
- **`creative/pipeline.py`**: Demonstrates the pattern of native `@pipeline` with `@phase` wrappers delegating to existing step implementations, plus `compile_pipeline()` attachment — directly applicable as the S2b extraction template.

### 4. What Still Must Be Built

1. **Native gate route authority**: Replace `AUTHORING_GATE(...)` handler delegation with source-owned gate semantics. The gate preflight, reprompt, downgrade, debt, severity policy must be declared policies on a native `@decision` or phase construct, not resolved by `_build_gate_route_signal` mutating `state['current_state']`.

2. **Native revise loop control**: Replace `AUTHORING_REVISE(...)` handler call with a bounded-loop native construct whose iterate/proceed/tiebreaker/abort/force-proceed outcomes are typed source exits, not handler-local state transitions.

3. **Loop cap and no-progress termination as source-visible policy**: The iteration cap (`_effective_critique_cap`), no-progress streak (`_critique_no_progress_streak`), and severity-gated termination branch (`_critique_terminate_branch`) must move from handler-local functions to declared loop policy on the native source construct.

4. **Split-outcome scenarios**: Master plan requires scenarios for gate reprompt/downgrade, critical cap exhaustion, cosmetic cap exhaustion, force-proceed, and abort (`master-plan.md:632`). Zero exist today beyond substrate-only golden traces.

5. **Dead-delete mutation tests**: Mutate/delete old front-half route groups in `components.py` and prove behavior unchanged under S2 scenarios vs frozen S1a baselines (`master-plan.md:633`).

6. **Severity schema enforcement**: Blocking North Star actions must be treated as correctness/security flags for loop caps and cannot be force-proceeded through the cosmetic branch (`NORTHSTAR.md:336–337`; `north-star-design.md:336–343`). This gate/review logic doesn't yet exist.

7. **Pre-sprint S0 plumbing**: North Star action schema (`gate.json`/`gate_carry.json` `north_star_actions[]`), revise prompt rendering, pre-worker halt guard, post-worker validation — none of this exists yet (`master-plan.md:344–401`).

---

### 5. Recommended Adjustment to the Sprint Plan

**S2 (Front-Half Native Loop) should be split into S2a (prep/plan/critique) and S2b (gate/revise)**, because gate/revise is the most semantically dense component in the entire Megaplan workflow:

- Gate alone carries 6 route signals (proceed, iterate, tiebreaker, escalate, abort, force-proceed), 3 revise reentries (iterate, retry_gate, reprompt_downgrade), 2 cap outcomes (critical→escalate, cosmetic→force-proceed), no-progress tracking, debt recording, preflight normalization, reprompt, and severity policy — all currently distributed across `handlers/gate.py` (1173 lines) and `components.py` (200+ lines of policy surface).

- The S0 North Star action plumbing (`master-plan.md:344–401`) is a prerequisite for any sprint that touches gate/revise semantics, because gate is the phase that creates North Star actions and routes them to revise. S0 must close before S2b extraction begins, or S2b will be building against a gate that cannot enforce the North Star severity schema.

- The master plan's S2 scope already acknowledges the coupling: "Gate/revise is one extraction unit because gate route groups and revise reentries are coupled (`components.py:1154–1158`, `:1276–1279`)" (`master-plan.md:624`). This coupling argument is correct, but S2 should still sequence: S2a extracts prep/plan/critique first (lower risk, fewer route signals), then S2b tackles gate/revise with S0 plumbing already in place.

- S2b exit gates should add: (a) North Star action blocking-severity integration test (blocking NS actions cannot be force-proceeded through cosmetic cap), (b) clean-context auditor can predict gate route from `.pypeline` source alone without reading `handlers/gate.py` or `components.py` route groups.
