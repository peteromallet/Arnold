### 3. What Can Be Reused or Generalized

1. **`gate_carry.json` as the North Star action carrier.** The master plan (lines 295-296, 338-339) specifies `north_star_actions` should travel through `gate.json`/`gate_carry.json`. The carry infrastructure already exists at `handlers/gate.py:270-308`; it needs a `north_star_actions` field added, not a new transport.

2. **Severity-gated termination pattern.** `_critique_terminate_branch` (466-520) already implements schema-assigned severity → blocking/force-proceed routing. This pattern directly generalizes to North Star action enforcement (master plan:333-337): blocking North Star actions should use the same correctness/security → BLOCKED, cosmetic → force-proceed branch.

3. **Reprompt/downgrade loop as the North Star enforcement pattern.** The reprompt path (993-1097) already demonstrates: gate detects unresolved issue → re-runs worker → auto-downgrades on persistent failure. North Star blocking actions would follow the same pattern: unresolved blocking action → routes to revise → gate re-checks.

4. **`REVISE_LOOP_POLICY` metadata as extraction target.** The policy metadata at `components.py:1239-1336` already declaratively specifies cap outcomes, severity policies, and termination rules. S2 extraction would make these source-visible in `.pypeline` constructs rather than component metadata.

5. **Boundary contracts for gate↔revise.** `boundary_contracts.py:107-138` can carry North Star enforcement rules as contract-level constraints.

### 4. What Still Must Be Built

1. **North Star action plumbing (S0 prerequisite) — entirely absent.** No `north_star_actions` field in gate/carry schema, no revise prompt rendering, no `north_star_actions_addressed` in `revise.json`, no pre-worker halt guard, no severity schema override in handler code. Zero code; all references are only in docs.

2. **Gate preflight as source-owned construct.** Preflight checks currently live in handler code (`gate_checks.py`, called from `handlers/gate.py:64`). Must be source-visible policy attachment.

3. **Debt recording as source-owned.** `_record_gate_debt_entries` (77-133) mutates state within the handler; must be a source-declared side effect of the gate step.

4. **Revise loop caps/no-progress termination as source-owned.** The cap logic (`_effective_critique_cap`, `_critique_no_progress_streak`) lives entirely in the handler. Must be declared policy on the loop construct.

5. **Tests.** No gate/revise loop tests or North Star action tests exist in `tests/arnold_pipelines/megaplan/`.

---

### 5. Recommended Adjustment to the Sprint Plan

**S0 must execute before S2 can close.** The North Star action plumbing is a hard prerequisite — S0 exit gates reference files (`test_north_star_actions_gate_revise.py`, `test_north_star_actions_review_blocking.py`) that don't exist. S2's scope includes "iterate/proceed/tiebreaker/abort/force-proceed" routing and "revise caps/no-progress" — both of which the master plan says must respect North Star blocking action semantics (lines 330-337: "Blocking North Star actions count like blocking correctness/security flags for loop caps and no-progress termination. They cannot be force-proceeded through the cosmetic/low-risk branch.").

**Risk:** If S2 extracts gate/revise into source without S0 North Star plumbing, the extraction will be incomplete — blocking North Star actions won't have a programmatic enforcement path, and the loop cap/force-proceed semantics won't distinguish North Star blocking from cosmetic flags. The `gate_carry.json` carrier that North Star actions need already exists; S0 should be scoped to add the `north_star_actions` field to what `_build_gate_carry` already produces, rather than building new transport.
