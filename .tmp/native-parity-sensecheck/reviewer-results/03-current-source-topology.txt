**Finding:** The same topology contracts (execute_batch, review_panel, tiebreaker_child) are declared in 3–4 different dicts/locations. The `DECLARED_WORKFLOW_TOPOLOGY_CONTRACTS` in `.pypeline` is not referenced by any runtime code path — `route_dispatch.py` reads `STEP_COMPONENTS_BY_ID` which reads `components.py` StepComponent objects.

**Consequence:** The pypeline's `DECLARED_WORKFLOW_TOPOLOGY_CONTRACTS` are **decorative** — changing them has zero effect on runtime behavior unless the lowering layer reads them (no evidence found that it does).

**Smallest corrective action:** Delete `.pypeline:281-385` entirely and re-route any consumer to `STEP_COMPONENTS_BY_ID[workflow_id].metadata["topology_contract"]`.

### GAP 2 (Critical): Pypeline Gate Route Bindings vs Policy Control Transitions — 8 vs 5

| Source | Route Bindings |
|--------|---------------|

### GAP 5 (High): Gate→force_proceed Bypasses Finalize-Execute Routing

`.pypeline:747-750`:
```python
finalize_payload = AUTHORING_FINALIZE(id="force_finalize", gate_payload=gate_route_signal)
AUTHORING_EXECUTE(id="force_execute", finalize_payload=finalize_payload)
```

**Finding:** This calls finalize as a function (discarding its routing) then directly calls execute — bypassing the declared `finalize:execute` route binding. The standard topology says finalize routes to execute; this path calls execute as a sibling, not as a downstream step.

**Consequence:** Any runtime that tracks step-to-step transitions (history, resume cursors) would see `finalize`→`execute` as a single-level parent-child, not as sequential steps. Resume from this state may mis-route.

**Smallest corrective action:** Replace with standard finalize→execute flow (remove the direct `AUTHORING_EXECUTE` call and let the finalize route binding carry control to execute).
