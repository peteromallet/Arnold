## Position

**Already-forbidden vs. genuinely permitted**: Exploits 3 (derived identity) and 11 (optimistic WBC write) are arguably already forbidden by the spirit of the documents but have literal wording gaps. Exploits 1, 2, 4, 5, 6, 8, 9, 10, 12 are **genuinely permitted** by the sprint briefs as written — each has an exact permitting sentence quoted above.

**Hidden route brain**: The central exploit pattern across all sprints is the dual-path routing architecture. The `.pypeline` → manifest path produces one topology; the handler `route_signal`/`next_step` → `_branch_edge_id` fallback maps AND the `workflow_data.py:WORKFLOW` dict produce two independent routing authorities. Any sprint that doesn't explicitly delete both legacy paths and prove their deletion leaves a route brain. The current architecture at `manifest_backend.py:227–312` preserves three fallback routing mechanisms (route_bindings lookup, hardcoded string maps for gate/tiebreaker/review, and override action dispatch), while `auto.py` preserves the `workflow_next` state machine. S3 and S6 briefs order deletion of *some* of these but the language is specific enough that an implementer can delete component route bindings while keeping the hardcoded string maps in `_branch_edge_id`.

**Recommendation**: The smallest fix with the highest leverage is deleting `_branch_edge_id` lines 246–312 and requiring that every route edge match comes exclusively from the compiled source topology with no string-matching fallback. Combined with deleting `workflow_data.py:WORKFLOW` and making auto-drive consume only the compiled manifest topology, this eliminates the dual-path architecture. Without this, every sprint's green proof can be manufactured by testing only the path where source and legacy agree.
