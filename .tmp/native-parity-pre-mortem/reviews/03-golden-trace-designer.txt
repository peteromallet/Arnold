# Isolated Review 3 — Golden Source-to-Runtime Trace Designer

## 1. Compact Executable Acceptance Oracle

Derived from the aspirational Python-authored workflow at `docs/arnold/megaplan-native-representation-report.md:613–720`. The oracle is the set of trace events any conforming execution MUST produce. It is expressed as a machine-checkable ordered-event schema.

### Oracle event types

| Event | Trigger | Mandatory fields |
|---|---|---|
| `phase.enter` | Any `@phase` call boundary | `semantic_node_id`, `parent_path`, `program_digest`, `policy_digest`, `wbc_contract_version` |
| `phase.exit` | Phase return (success) | As above + `outcome_type` |
| `decision.evaluate` | Any `@decision` call | `decision_id`, `vocabulary_set`, `inputs_hash` |
| `decision.accept` | Decision outcome chosen | `decision_id`, `accepted_outcome`, `ra_decision_id`, `ra_fence_seq`, `cas_seq` |
| `decision.consume` | Runtime transition consumes decision | `ra_decision_id`, `consumed_by_node`, `transition_action`, `outcome_match` |
| `loop.enter` | While-loop entry | `loop_id`, `max_iterations`, `iteration` |
| `loop.exit` | Loop exit (typed) | `loop_id`, `exit_kind` ∈ {`proceed`, `cap_exhausted_critical`, `cap_exhausted_cosmetic`, `abort`} |
| `fanout.dispatch` | Dynamic map item dispatched | `fanout_id`, `child_semantic_path`, `item_identity` (task_id + batch_id + item_path) |
| `fanout.collect` | Reducer runs | `fanout_id`, `child_count`, `reducer_id` |
| `human.suspend` | Suspension reached | `suspension_id`, `capability`, `reentry_path`, `wbc_lineage` |
| `human.resume` | Resume from suspension | `reentry_path`, `ra_decision_id`, `custody_epoch`, `lease_owner`, `program_digest` (must match) |
| `custody.acquire` | Lease acquired | `target`, `epoch`, `owner_pid` |
| `custody.renew` | Lease renewal | `target`, `old_epoch`, `new_epoch` |
| `custody.release` | Lease released | `target`, `epoch` |
| `wbc.effect_intent` | Pre-effect boundary | `boundary_version`, `intent_id`, `node_id` |
| `wbc.effect_outcome` | Post-effect boundary | `intent_id`, `outcome`, `idempotency_key` |
| `checkpoint.write` | Durable checkpoint | `semantic_path`, `program_digest`, `policy_digest`, `wbc_version` |
| `checkpoint.resume` | Resume from checkpoint | `semantic_path`, `must_match`: {program, policy, wbc_version}, `drift_disposition` |
| `terminal.accept` | Terminal outcome | `result_kind` ∈ {`done`, `aborted`, `blocked`}, `ra_decision_id` |

### Oracle predicates (must be true for every trace)

1. **Set equality**: Authored semantic node/child set == lowered node/child set == runtime WBC-producer set.
2. **Decision closure**: Every typed decision occurrence has exactly one `decision.accept` with matching outcome and exactly one `decision.consume` with matching `ra_decision_id`/CAS.
3. **Four-domain separation**: No single ID appears in more than one of: semantic path, RA subject attempt/fence, WBC attempt, custody lease.
4. **Causal joins**: Every `fanout.dispatch` child has explicit parent→child WBC attempt join.
5. **Checkpoint integrity**: Every `checkpoint.resume` verifies program/policy/WBC-version digests match the pinned originals, or records an explicit `migration`/`new_attempt`/`quarantine` decision.
6. **No string-routing**: No handler-returned string (`next_step`, `route_signal`, `recommendation`, `verdict`) appears as an event source for any routing transition.
7. **Authority before action**: Every `custody.acquire` or `phase.enter` with authority-increasing effect is preceded by a current RA grant/fence in the trace.

## 3. S1–S7 Plan-Gap Verdict

### DECISIVE VERDICT: The current S1–S7 wording does NOT necessarily produce the six golden traces. Three gaps are fatal.

#### Gap 1 — No dynamic fanout identity specification (FATAL)

**Evidence**: S2 defines dynamic map/reducer (`briefs/s2-front-half-native-loop.md:13`) and requires "deterministic child naming" (`:14`), "deterministic semantic identity" (`:23`), and states "collision tests prove identity is semantic, not list-position-only" (`:52`). S5 requires "deterministic semantic child coordinates containing task ID, batch identity, and item path; list index alone is forbidden" (`s5-review-rework-finalize.md:29–30`).

**The gap**: Neither S2 nor S5 specifies the concrete identity schema. They say what it must NOT be (list index) but not what it IS. The acceptance oracle requires `task_id + batch_identity + item_path`. Without this specification, two independent implementations will produce incompatible fanout identities. This breaks scenarios 2, 4, and 5.

**Fix**: Add to S2 deliverables: a concrete `ChildIdentity` schema `{task_id: str, batch_id: str, item_path: str}` with a deterministic serialization format, plus a reference collision test with concrete inputs.

#### Gap 2 — Decision-occurrence to RA-decision to consumed-transition wiring is underspecified (FATAL)

**Evidence**: S1 mentions "accepted Run Authority decision ID, outcome, and CAS sequence" (`s1-checker-outcomes-builder-slice.md:30–31`). S2 requires "Every closed typed decision... creates or links exactly one accepted Run Authority Decision" (`s2-front-half-native-loop.md:30–33`). The corrective plan requires this (`docs/arnold/megaplan-native-parity-corrective-plan.md:132–138`).

**The gap**: No sprint specifies HOW the link is established. Is it:
- (a) The decision call site emits the RA decision ID into the trace?
- (b) The runtime transition reads the ID from a shared store?
- (c) The compiler statically binds them?

Without this, scenarios 1–6 cannot produce the required `decision.accept` → `decision.consume` pairing with deterministic IDs. The oracle's "exactly one" constraint cannot be verified.

**Fix**: Add to S2: a `DecisionBinding` protocol specifying that each `@decision` call site produces a `(decision_id, ra_decision_id, cas_seq)` triple written to the WBC attempt record before the dependent transition executes, and the runtime must consume that exact triple.

#### Gap 3 — Program/policy/WBC-version drift detection lacks concrete digest algorithm (FATAL)

**Evidence**: S2 requires "Bind every checkpoint/reentry envelope to the authored program/topology digest, call-site-policy digest, and exact WBC boundary-contract version" (`s2-front-half-native-loop.md:37–42`). S4 extends this to suspension (`s4-execute-dag-approval-resume.md:52–54`).

**The gap**: No sprint defines what "program/topology digest" or "call-site-policy digest" means. Is it:
- Source-file SHA256?
- Lowered IR hash?
- AST structural hash?
- Semantic hash of the lowered graph?

Different choices produce different resume behavior. Scenario 3 (cross-host resume) critically depends on this—resume must verify the exact same digest was pinned at suspend time. Without specification, silent drift is possible.

**Fix**: Add to S2: the digest algorithm is `SHA256(lowered_ir_canonical_form + policy_manifest_canonical_form)`. The lowered IR canonical form must be specified (sorted keys, stable node ordering).

#### Secondary gaps (non-fatal but high-risk)

4. **S3's internal stop/go gate lacks concrete pass criteria** (`s3-tiebreaker-replan-native.md:11–20`). It says "emit a green builder/adoption receipt" but the receipt format is deferred to S1's proof-map schema. If S1's schema is incomplete, S3's gate is unenforceable.

5. **S6's override effect-only actions** (`s6-override-auto-compat-collapse.md:16–18`) reference "exact target, current required authority/custody, durable WBC effect history, and an explicit `no_route_change` outcome" but never specify the `add-note` WBC schema, leaving scenario 6's effect-only note path unvalidatable.

6. **S5's cycle is described as "one reusable authored cycle"** (`s5-review-rework-finalize.md:48`) but the current `.pypeline` at `arnold_pipelines/megaplan/workflows/workflow.pypeline:388–754` hardcodes separate execute/review/rework chains for gate-proceed, tiebreaker-proceed, and override-force-proceed paths—each with its own rework duplicate block. S5's wording does not require collapsing these, so the "one" cycle may remain three copies.
