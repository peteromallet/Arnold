## 3. Safe Strangler Order (Position)

**The chain must be re-ordered into 9 PRs across 7 sprints to avoid the deadlocks identified in §2.**

### PR1 (S1) — Admission + Checker + Proof-map Schema
No change to product code. Builds `final-proof-map.json` schema, validator receipt contract, and negative fixtures. Only the checker infrastructure changes. **Repo runnable at every commit.**

### PR2 (S2) — Generic Constructs + Reference Pipeline
Compiler changes only. Megaplan product code untouched. Reference pipeline is a separate test file, not Megaplan. **Repo runnable at every commit.**

### PR3 (S3 stop/go) — Vertical Slice with Dual Carriers
Add prep→plan native topology alongside existing carriers. Both old and new carriers live. The stop/go receipt proves the new carrier is load-bearing by: (a) mutating source changes trace, (b) mutating old carrier does not. **Repo runnable — old carrier still routes execution.**

### PR4 (S3 carrier fence) — Quarantine, Not Delete
After PR3 receipt passes: **hard-fence** front-half carriers (raise or no-op on read), do not delete files. The fencing makes every consumer that reads the old route authority get a deterministic failure unless it has migrated to the new topology reader. This forces:
- `auto.py` → read from lowered topology API (already exists at `planning.py:resolve_lowered_route_target_for_signal`)
- `_core/workflow.py` → `workflow_next()` reads from lowered topology, not `workflow_data`
- `_core/topology.py` → `RunTopology.next_steps()` reads from lowered topology
- `cli/` → reads from lowered topology

**This PR does the wire-up that PR7's bugfix was supposed to do.** Repo runnable because consumers are updated before the old producers are removed.

### PR5 (S4) — Tiebreaker + Finalize + Human Decisions
Applies the same dual-carrier→fence pattern to tiebreaker and finalize surfaces. First add authored topology alongside handlers (dual-run), then fence old carriers after green receipt. **Repo runnable per sub-step.**

### PR6 (S5 step 1) — Execute/Review Authored (add phase)
Add execute and review as authored topology alongside existing handler-based execution. Dual-run. **Repo runnable — old handlers still work.**

### PR7 (S5 step 2) — Fence execute/review carriers
Fence old execute/review route authorities. Consumers were already updated in PR4 for the general pattern. **Repo runnable.**

### PR8 (S6) — Override + Auto + Projection Reduction
Authored override actions. Reduce auto.py to event consumer. Fence remaining `_core` routes, CLI translation, LEGACY_ALIASES, handler action dispatch. **Repo runnable because consumer migration was done in PR4.**

### PR9 (S7) — Final Conformance
Extend M11 proof framework. Run end-to-end with wheel/sdist/cloud. The `final_conformance_gate` consumes the complete proof-map and pre-receipt hash. **Repo runnable.**

## 5. Rollback Points

**Every PR boundary is a valid rollback point.** Within a PR, the strangler pattern (add carrier → fence carrier in separate commits) provides sub-step recovery:

- **PR3 commit 1** (add authored prep→plan) → rollback = delete new topology, keep old carrier
- **PR3 commit 2** (dual-run wiring) → rollback = revert wire-up, old carrier still works
- **PR4 commit 1** (consumer migration) → rollback = keep old consumer code
- **PR4 commit 2** (old carrier fence) → rollback = unfence, old carrier still works

The **critical rollback constraint**: once old carriers are fenced (PR4/PR7/PR8), rolling back the fence commit without also reverting the consumer migration commit leaves consumers reading from a non-existent topology. **Rollback must be commit-atomically paired**: consumer migration + fencing in a single revert.
