# Megaplan — how it SHOULD work (intended design)

**Generated:** 2026-08-07 (UTC) — consolidated from a 6-agent intended-design survey (chain runner, custody, resident, fixer stack, cloud runtime, evidence/gates) of the local durable line + cloud box code. This is the canonical briefing of the INTENDED operating model, used as the anchor surfaced to the DeepSeek Flash fixer prompt and the codex planner.

## Summary

Megaplan is an enforced-rigor planning and execution spine that drives ~2-week plans through a fixed phase state machine (prep→plan→critique→gate→revise→finalize→execute→review→done) and multi-milestone work through an ordered chain of plans (chain.yaml). Its core design bet is the judgment/labor split: frontier models plan, critique, gate, and review; cheaper models do the high-volume labor; the harness enforces every step so a weak model cannot silently claim completion. The whole machinery runs unattended on a Hetzner agentbox behind a thin stable bootstrap image, with all engine code propagating through a single durable branch (origin/editible-install) refreshed and pip-installed on the volume. A always-on Discord resident is the human's interface: it schedules recurring work, dispatches managed subagents, verifies completions, and delivers synthesis. A layered fixer stack (watchdog → L1 repair → L2/L3 meta-repair → progress auditor) keeps chains alive and durably advancing under a mechanical lease so no competing fixers ever run. A custody control plane makes the derived-state-drift failure class impossible: exact content-addressed action-target identity, renewable exclusive leases with epochs, and a double-fenced action gate that re-reads Run Authority + Custody + WBC durable stores at every authority-increasing action. Everything emits content-addressed evidence (events.ndjson journals, WBC step receipts, proof maps, completion manifests, validation receipts) so "done" is a claim confirmed from objective evidence — never from status prose, heartbeat, PIDs, or model self-report. The intended end-state has a single promoted base runtime that the resident executes and the fixer edits; the current running state is a mid-flight migration toward that target.

## Operating model

Megaplan is organized as six cooperating planes that together turn a committed brief into a durable, evidence-backed, unattended "done". (1) The CHAIN RUNNER is the spine: work is sized to ~2-week plans, with three dials (profile=overall difficulty, robustness=process completeness, depth=tokens per call) chosen at init and the brief snapshotted so later edits are not re-read. Bigger work becomes an epic decomposed into milestone briefs plus a chain.yaml spec. Each plan is driven through a canonical phase ladder (prep→plan→critique→gate→revise→finalize→execute→review→done) with require_state-guarded transitions, a critique→revise loop re-entering at critique, and a gate that routes PROCEED/ITERATE/ESCALATE/TIEBREAKER. Judgment (planning, critique-lens selection, gate adjudication, difficulty scoring, review) is always separated from high-volume labor (prep digging, critique lenses, execution batches). The 'auto' driver is the intentionally-dumb unattended loop that advances until a terminal state; 'resume' is the single-step recovery verb that re-enters the exact phase named by a persisted resume_cursor. State persists and resumes deterministically so one failing milestone never loses prior milestones' work, and failures halt by default rather than silently degrading. (2) The CUSTODY CONTROL PLANE is the exclusivity/ownership substrate layered under every authority boundary: work is reduced to an exact content-addressed identity (F01 repair-occurrence tuple + chain identity → SHA-256 digest), a lease is acquired for a bounded epoch under a current Run Authority grant/fence with a WBC attempt reference, and every transition is an immutable append-only lease event. Before any authority-increasing action (dispatch, repair, completion, cancellation, publication, delivery), a double-fenced validator re-reads the current Run Authority grant/fence, the current Custody lease/epoch, and the required WBC evidence from durable stores — any stale half rejects. Custody makes competing owners, orphaned work, and stale-owner action mechanically impossible. (3) The RESIDENT is the always-on, durable human-facing operator: it owns converse, schedule, delegate, deliver. A thin Discord listener maps every eligible message to exactly one turn through a burst coalescer; a durable schedule layer materializes immutable occurrences under immutable authorization grants and enforces hierarchical concurrency admission (max_active=1 default, overlap=forbid); managed subagents are launched with a content-addressed manifest, git-custody evidence for mutations, completion verification against the effect claim, and single-owner synthesis/delivery. The resident reads the same canonical cloud-status snapshot the watchdog produces; it is NOT the chain runner, watchdog, or deploy machinery. (4) The FIXER STACK is the repair machinery: a 1h watchdog observes and classifies every cloud session, a repair-trigger runs a shared conservative classifier and claims a singleton blocker, an L1 repair-loop holds a per-session lock and tries cheap mechanical repairs then bounded investigate-mutate turns re-driving the chain via auto/resume until durable movement is proven, an L2/L3 meta-repair-loop (Codex orchestrator + DeepSeek subagents) fixes the fixer at source, a 6h progress auditor judges whether the superfixer itself is working, and an hourly meta-loop supervises the superfixer. Its three defining qualities: no competing fixers (mechanical lock/lease), evidence-gated recovery (never success without durable movement proof), and structural fixer-layer issues surfaced to the epic/session ticket. (5) The CLOUD RUNTIME is a thin stable bootstrap image whose operational logic ships through an on-volume source clone refreshed from origin/editible-install, one cloud.yaml per initiative as the deployment manifest, an immutable content-addressed runtime per promoted commit selected by durable selector files, and the watchdog as process supervisor with host systemd ensure-timers as the singleton recovery mechanism (the "never dark" guarantee). Everything runs un-pushed nowhere and is deleted only when closed. (6) EVIDENCE + GATES is the proof discipline that makes the judgment/labor split safe: an ascending chain from raw run IDs → events.ndjson → WBC step receipts + phase artifacts → review evidence → proof-map.json → completion-manifest.json → validation receipts → launch preconditions. Gates decide continuation, evidence records objective facts, and verification re-derives verdicts from evidence (CompletionVerdict). "Done" is a claim confirmed from content-addressed evidence; structural/underlying issues surface into durable tickets, the critique ledger, and the fixer-session index rather than vanishing by paraphrase.

## End-to-end flow

INITIATION. An author sizes the work: ~2 weeks = a single plan; bigger = an epic decomposed into milestone briefs. They write the brief under .megaplan/initiatives/<slug>/briefs/, a NORTHSTAR.md, chain.yaml (milestones, merge_policy, launch_preconditions, gates), and cloud.yaml (provider, repo, mode, agents, source ref, secrets), choosing profile/robustness/depth dials. For single plans, megaplan init snapshots the brief and north-star anchors and creates the plan dir at current_state=initialized. For epics, cloud preflight validates spec layout/north star/brief paths/resolved routing/secrets, then cloud chain (or launch-epic) FAIL-CLOSED syncs the local launch HEAD to origin/editible-install, uploads spec + idea files + anchors to the derived isolated workspace, seeds OAuth, launches the chain runner in a derived tmux session, writes the cloud-session marker + last_chain.json, and verifies watchdog tracking and liveness before emitting provenance JSON.

NORMAL OPERATION. Inside the container, the chain runner drives milestone plans through the phase ladder: prep (optional research, may halt for clarification) → plan (frontier model authors plan + success criteria) → critique (judge evaluates across lenses; adaptive critique picks lenses via a premium evaluator) → gate (typed PROCEED/ITERATE/ESCALATE/TIEBREAKER + preflight) → revise (re-author addressing every flag, back to planned) → finalize (task difficulty 1-10 tier ladder + test baseline) → execute (batches dispatched by tier to the cheapest capable model, escalating to premium on failure streaks) → review (verify against success criteria + tests + evidence; rework loop finalized↔executed with a cap; deferred must criteria → awaiting_human_verify) → done (completion authority + completion contract, then publish/PR per merge_policy). Each phase writes a step receipt + phase artifact + events.ndjson entries. The auto driver advances unattended; on a PR branch it commits+pushes each phase. The resident drives runs via its subagent launcher and reports progress to Discord; the watchdog observes each session hourly and classifies it.

FAILURE. If a chain stalls, fails, or a phase errors, the driver bails to a recorded failure with resume_cursor + retry_strategy. The watchdog observes the unintended nonterminal condition, classifies it via the shared classifier (conservative — unknown shapes never auto-dispatch), and enqueues a repair request. repair-trigger coalesces by signature, claims a singleton blocker under a trigger lock, and dispatches repair-loop. L1 holds a per-session repair lock, tries cheap mechanical repairs (each verified by live_with_fresh_activity), then bounded investigate-mutate turns with escalating models, re-driving via megaplan auto/resume until durable milestone movement is proven; a deterministic-failure breaker and real exhaustion escalate to Discord DM + needs-human marker. If one of six meta-repair triggers matches, meta-repair-loop (Codex orchestrator + DeepSeek research subagents, recursion-guarded) diagnoses at root, applies a narrow source fix to the approved editable runtime, retriggers L1, and verifies terminal success from an authoritative post-retrigger snapshot, persisting a redacted record. The 6h progress auditor judges whether the superfixer itself worked (FIXED <sha>/PASSIVE) and fixes watchdog/trigger/auditor bugs at source; the hourly meta-loop verifies the whole superfixer. All of this passes through custody: the repair occurrence is reduced to an exact F01 identity, a lease is acquired under the current Run Authority grant/fence with the WBC attempt reference, and every authority-increasing action is double-fenced against the durable stores. Human-required decisions surface to the resident as escalations and are answered through exact-phrase confirmation under a repair lock.

REPAIR/ESCALATION. A human (via the resident) answers escalations, approves gates, or resolves quality gates; awaiting_pr_merge respects merge_policy review/manual. If the autonomy ladder is walked to exhaustion (bounded retry → bump profile/robustness once → abort), a chain_ladder_exhaustion ticket is auto-filed. Structural/underlying fixer issues are persisted to the epic/session ticket and /workspace/repair-findings/persistent-problems.md, and fixer-session summaries/index.md are git-committed as untrusted historical evidence.

COMPLETION. A milestone is done when the plan reaches done via a successful review, the completion guard passes (plan current_state==done or merged-PR bypass with nonempty semantic diff / typed no-op waiver), the post-merge final_conformance_gate runs the declared validator subprocess and validates its receipt against current content hashes, the receipt is appended to the proof map, the completed record is appended behind the chain completion guard, and completion-manifest.json (schema arnold.megaplan.chain_completion_manifest.v1) is written beside the chain spec with sha256 proof artifacts per milestone. Downstream milestones/chains with chain_completed+require_manifest launch preconditions re-validate the predecessor manifest byte-for-byte before initializing; successors must run sequentially in the same checkout so custody/acceptance records are visible. On chain completion the runtime is promoted: build an immutable runtime from the reviewed FINAL_SHA, run an isolated read-only canary, atomically rewrite the three durable selector surfaces under a host cutover lock, rebind chain state + marker to the candidate content_sha256 via runtime-rebind CAS + runtime_cutover, deploy+restart through systemd ensure units, run production acceptance cycles (0/5/10-min probes), and emit release receipts. Closed runtimes are GC'd only after closure + origin-resolution. Durable engine fixes are continuously transactional-promoted back to base (never ahead of origin, import-smoke-tested, atomically FF-pushed) so nothing runs un-pushed and nothing is deleted unclosed.

## Components

### Chain Runner / Plan Lifecycle

**Role:** The orchestration spine: takes a committed brief and drives it through a fixed sequence of judgment/labor phases to an evidence-backed done, and drives multi-milestone work (epics) as an ordered chain of milestone plans. Separates all real judgment (planning, critique-lens selection, gate adjudication, difficulty scoring, review) from high-volume labor (prep digging, critique lenses, execution batches) and enforces every step by harness so a weak model cannot claim completion.

**How it works:** Sizing: work is ~2 weeks per plan; three dials (profile/robustness/depth) chosen at init and the brief snapshotted (later edits not re-read); bigger work = epic with milestone briefs + chain.yaml. init creates .megaplan/plans/<name>/ with state.json (current_state=initialized) and captures north-star anchors. A phase state machine (prep→plan→critique→gate→revise→finalize→execute→review→done, plus aborted/failed/blocked/paused/awaiting_human/tiebreaker off-ladder states) guards every transition via require_state. Robustness shapes the workflow (bare=plan→finalize→execute; full default=prep→plan→critique→gate→revise→finalize→execute→review with up to 6 critique lenses; thorough/extreme add lenses and parallel review). The gate maps critique verdicts to typed PROCEED/ITERATE/ESCALATE/TIEBREAKER recommendations and runs preflight. auto is the 'intentionally dumb' unattended drive loop (stall detection, bounded retries, cost cap, execute-tier escalation, review-rework cap, gate-ESCALATE force-proceed default); resume is the single-step recovery verb that re-enters the exact phase named by a persisted resume_cursor, refuses to resume across a changed pipeline manifest, and clears the cursor on success. chain start loads the spec, validates anchor/paths/preflight, and drives each milestone via the auto loop with a per-milestone rubric, an autonomy ladder (bounded retry→bump profile/robustness once→abort→auto-file ladder ticket), post-merge final_conformance_gate, an append-guarded completion record, and a completion-manifest.json. merge_policy auto (default) enables auto-merge vs review/manual (parks at awaiting_pr_merge).

**Interactions:**
- Resident layer: resident schedules and drives unattended runs by invoking megaplan auto / chain start via its subagent launcher and reports chain progress (milestone index / current plan / last state) through Discord; chain policy (auto_approve, stall thresholds) is honored by the resident drive loop.
- Custody: milestone completion and completion records pass authority checks (_plan_terminal_completion_is_authoritative, completion guard, accepted-execution projection); box chain modules (source_admission, target_rebind, wbc, fresh_child_launch) bridge chain advancement with custody admission/controlled writers.
- Fixer stack: watchdog observes plan/chain state and classifies live/blocked/stalled; repair-loop and superfixer re-drive stalled milestones respecting plan-level locks; advancement.py is the single-source policy so watchdog, schedulers, and the chain agree on when the cursor may move without a person.
- Cloud runtime: chains run unattended in the cloud container (cloud.yaml mode: chain); cloud status/logs/attach observe; the cloud supervisor restarts dead runners or advances past merged PRs while refusing unsafe actions.
- Evidence + gates: chain/proof-map and completion-manifest.json feed the evidence layer; gate checks, receipts, and the full-suite backstop gate milestone completion; ladder-exhaustion tickets auto-file into the ticket/ledger system.
- Publish/PR surface: chain drives git branch/PR lifecycle (branch, per-phase commit+push, PR + auto-merge or awaiting_pr_merge) via git_ops.py and supervisor/pr_merge.py.

**Invariants:**
- Single-driver: plan-level advisory lock (lock_acquired/lock_released); the auto driver clears orphaned/stale active_step before redispatch and quarantines half-written phase output; chain refuses to run a plan with a live active step.
- State transitions are guarded: each phase checks require_state and raises invalid_transition with valid_next; the WORKFLOW transition table is the single source of truth.
- Stall detection: same state for stall_threshold iterations with no forward progress bails the driver; all-blocked-no-pending execute is treated as poisoned, distinct from a generic stall.
- Bounded retries, never infinite loops: context/external/blocked/add-note/repeated-failure-signature/review-rework/critique-iteration caps each bail to a recorded failure with resume_cursor + retry_strategy.
- Cost cap: cumulative history cost > max_cost_usd aborts automation after a phase completes.
- Completion authority: execute completion must be corroborated (finalize + execution artifacts); resume refuses to advance past execute without authority; chain completion guard requires plan done (or merged-PR bypass) plus published semantic diff nonempty from base or a typed no-op waiver.
- Critique==review: the same non-author model critiques the plan and reviews executed work; partnered profiles keep the premium evaluator as director.
- Failure semantics: on_failure/on_escalate default stop_chain; retry_milestone bounded by a persisted per-label counter; ladder = bounded retry → bump profile/robustness once → abort; apex/extreme cap at 1 retry.
- Anchor requirement: chains require anchors.north_star by default; milestones only extend the epic anchor.
- Topological assertion: milestone depends_on is a serial-in-listed-order assertion; final_conformance_gate validation only on the final milestone.
- Clean base: require_clean_base asserts no carried WIP before milestone init; stashes locally under --no-push, fails loud under CI so real work is never silently discarded.
- PR progression: merged-PR claims reconciled from ground truth; stale closed PR stops the chain; awaiting_pr_merge respects merge_policy; completion records append-guarded.
- Evidence-gated completion: completion-manifest.json requires sha256 proof artifacts per milestone; launch_preconditions verify manifest rows + current content hash together — bare contains_text/exists is never evidence of a predecessor relationship.

### Custody Control Plane

**Role:** The exclusivity/ownership substrate and third leg of the tripartite authority model (Run Authority + WBC + Custody) that composes at every action boundary. It is the sole owner of exact action-target/repair-occurrence identity, renewable exclusive leases, custody epochs, transfer/reclaim/release/expiry, and reconciliation, and it makes the derived-state-drift failure class mechanically impossible: no watchdog, repair, status, or resident path may turn cached/derived state (projections, PIDs, markers, receipts, labels, liveness) into positive authority to act.

**How it works:** Work needing exclusivity is reduced to a canonical CustodyTargetKey (the F01 repair-occurrence tuple: environment, session, chain, plan_revision, phase, task, attempt, normalized_failure_kind, blocker_or_phase_result_hash, fence, plus chain_identity) giving a deterministic SHA-256 digest; RepairOccurrenceKey wraps it with run_id/run_revision/coordinator_attempt_id/fence_token/wbc_attempt_reference. A CustodyLease is acquired via lifecycle-helper (owner host/pid/boot_id bound to the occurrence for a bounded epoch — default TTL 30min, grace 5min, hard ceiling 24h) referencing the Run Authority grant id, coordinator fence token, and WBC attempt reference, with idempotency key + causal predecessor. Every transition (acquire/renew/transfer/release/expire/fence/conflict/reconcile) is an immutable CustodyLeaseEvent appended to a per-lease JSONL history under ~/.megaplan/custody/leases; state is derived only by deterministic replay. Before ANY authority-increasing action, the action validator double-fences: it REREADS current Run Authority grant/fence, current Custody lease/epoch, and required WBC attempt status from durable stores (never projections), and all three must be satisfied — either stale half rejects. Every authority-increasing writer is registered in a controlled-writer registry (report_only/shadow/active) and fails closed until promoted. Cross-owner references go through a durable outbox with reconciliation/dead-lettering. Repair receipts are signed/content-addressed and adopted verify-only against current grant/lease/epoch/revision/contract/tree/tests/fence; mismatch quarantines the receipt and resumes normal execution without rewriting history. A terminal/expired/fenced lease may be reclaimed by a new owner with a strictly greater epoch; cross-host transfer requires the old epoch durably fenced first. Recovery is event-driven with a p95 <5min accepted-repair-or-typed-escalation SLO, with periodic scan + backstop (six-hour auditor, later three-hour) as reconciliation only, never the primary scheduler. A repair actor can never verify itself; closure requires an independent verifier proving negative control plus resumed authoritative progress.

**Interactions:**
- Run Authority: custody leases reference (read-only) the Run Authority grant id and coordinator fence token; every authoritative action requires BOTH current RA grant+fence AND current Custody lease+epoch; RA owns grants/decisions/quarantine, Custody owns exclusivity/epochs — neither substitutes for the other.
- WBC (Workflow Boundary Contracts): custody references the WBC attempt reference and F01 occurrence digest; required WBC attempt/effect evidence is validated at the declared boundary from the WBC store; WBC never grants or leases authority and Custody never duplicates WBC's ledger.
- Fixer stack: repair dispatch eligibility is gated on the exact repair-occurrence identity tuple + current lease/epoch + current RA fence; the repair actor holds the lease; a reclaim/transfer re-epochs it; the L3 auditor audits the resolver and L2 and can escalate to human.
- Resident layer: the resident records a git-custody launch target before launching a delegated agent and treats a successful model exit as completion only after a machine-readable receipt proves isolation/verification/integration or a launch-time ambiguity gate; managed child runs emit append-only custody events with launch provenance and a delivery_custody projection.
- Escalation: escalations.py gives ledger-backed authorization for escalation answers; L3 auditor_escalate_to_human is the audit-the-auditor backstop.
- Completion/acceptance: Custody M11 is the predecessor of the completion kernel and downstream chains; chain_completed with require_manifest gates successors, and successors run sequentially in the same checkout so a completed predecessor's custody/acceptance records are visible.

**Invariants:**
- Single-owner: Custody is the ONLY owner of lease state and exact action-target/repair-occurrence identity; cross-owner references are read-only pointers, never duplicate ledgers.
- No competing owners: acquire is rejected when an active lease exists; a lease may only be re-acquired after release/expire/fence, and reclaim requires a strictly greater custody epoch (old-epoch fencing).
- No orphaned work: leases have bounded TTL + grace; expiry is terminal and sweepable; release/expire/fence are terminal and appended, never truncating history.
- Immutable receipts/history: events and attempts are append-only; sequence monotonic; idempotency key + payload hash must match for a no-op, same-key/different-payload hard-conflicts and quarantines; deterministic replay must reconstruct identical state.
- Double-fenced action boundary: every authority-increasing action validates current RA grant/fence AND current Custody lease/epoch AND required WBC evidence by REREADING durable sources at action time; projections, markers, PIDs, logs, receipts, status, and liveness are evidence/rebuildable projections only and never authorize action.
- Fail-closed: unregistered writer → denied; shadow-only production write → DENIED; unknown/incoherent result → no dispatch/retry/success; manual_review is never a dispatch policy.
- Exact repair identity: the F01 tuple must be complete and current; a stale occurrence cannot bind to a newer target; duplicate/late/out-of-order triggers launch at most one current managed repair or remain visibly pending.
- No self-verification: a repair actor cannot verify itself; recovery closes only after independent negative-control evidence plus resumed authoritative progress; liveness is not success.
- Monotonic epoch + owner identity: renew/transfer/fence require the caller to be current owner and the new epoch monotonic; transferred/expired/fenced owners cannot renew, complete, cancel, publish, or deliver after handoff.
- Projection purity: observers do not refresh liveness/custody/progress; state.json, chain JSON, markers, and journals are downstream projections/evidence adapters only.
- Shadow-first rollout: all custody writers start report_only/shadow; production enforcement is off (ARNOLD_M7_ACTION_VALIDATOR_ENFORCEMENT default 0) until machine-verifiable acceptance; promotion is explicit, never silent.
- TTL ceiling + recurrence floor: no lease exceeds 24h; repair recurrence cannot dispatch the same problem signature more often than the 120s minimum interval.

### Resident Layer

**Role:** The always-on, durable human-facing operator of Megaplan. It is the human's interface: answers 'what's running / how's it going' from canonical status, shapes epics/sprints/checklists/initiatives, kicks off and babysits cloud chains, runs scheduled recurring work, dispatches delegated subagents, verifies completions, synthesizes and delivers results to Discord, answers escalation prompts, and can launch D10 fix-the-fixer meta-repair. It is NOT the chain runner, NOT the watchdog/repair-loop, and NOT the cloud deploy machinery — the watchdog owns 'is it alive and healthy', the resident owns 'converse, schedule, delegate, deliver', and both read the same canonical cloud-status snapshot.

**How it works:** Four cooperating layers. (1) Transport + runtime loop: a thin Discord listener maps every non-bot message to an InboundEvent with a deterministic idempotency key, authorizes against allowlists, handles escalation-answer replies (ledger + exact-phrase confirmation + repair lock before resume), and routes: direct commands execute immediately; managed-agent follow-ups continue the exact recent session; everything else goes through an AsyncBurstCoalescer that folds rapid adjacent messages into one burst, creating exactly one Turn (prompt_snapshot, state_at_turn, model_version). An AgentRunner (OpenAI-compatible over openrouter/openai, or CodexCliAgentRunner over codex exec) runs bounded model/tool rounds; the final text is redacted, persisted as an outbound Message with an idempotency key, delivered through the OutboundSink (Discord chunked <2000 chars). Crash-before-outbound may retry; crash-after-outbound never resends. (2) Hot context: profile.load_hot_context() assembles the canonical orientation — the watchdog-produced cloud-status snapshot (stale snapshots stripped of numbers + verbatim WATCHDOG STALE banner), live-cloud-chain projection, initiative compact index, schedule hot context, knowledge roll-up (document→ticket→initiative lifecycle), runtime identity, timezone. (3) Schedule layer: a durable scheduler owns timing and admission; the rich ScheduleDefinition surface has an OWNER + immutable AuthorizationGrant (content-addressed digest, max_work_intent, launch_origin, route_ref), a Timing (at/delay/interval/cron/calendar/event), Bounds, Policies (misfire, overlap allow/forbid/queue, concurrency_key, max_active=1 default, quota_breach), a Target (managed_agent or orchestrator_turn with pinned prompt digest), Delivery (exact_authorized_route == grant route_ref), RetryPolicy and Quota (fail-closed accounting). It materializes immutable occurrences with content-addressed receipts, claims under a lease with stale-claim reclaim, and enforces a hierarchical concurrency admission ladder before launch. (4) Managed delegation: launch_subagent_task routes by kind/difficulty to model (luna for mechanical D1-3, terra routine, sol/high for high-risk/D7-10), selects provider backend, writes an arnold-managed-agent-run-v2 manifest, spawns the provider subprocess, normalizes provider streams into a shared event contract, records provenance, enforces git-custody evidence for mutations (and forbids git evidence for non-mutating runs), aggregates into one synthesis_delivery_owner, sweeps delivery with retries, supports follow-ups and queued successors. Scheduled jobs and one-off requests land in the same durable machinery.

**Interactions:**
- Discord transport: ResidentDiscordService listener, DiscordOutboundSink (chunked, durable ids), reactions (whats-cooking toggle), follow-ups, mark_processing lifecycle, voice transcription.
- Megaplan Store: persists conversations, messages (inbound/outbound with idempotency keys), turns (prompt_snapshot/state_at_turn), tool-call audit records, cloud_runs, scheduled_jobs, control_messages, progress_events, system_logs.
- Watchdog status pipeline: reads the canonical /workspace/.megaplan/status/cloud-status.json snapshot as FIRST source for broad status; never SSHes to its own host.
- Cloud CLI backend: constrained cloud operations (status/chain/bootstrap/resume/logs) mapped to CloudRun + progress events.
- Control plane: queues control messages (approve_gate/reject_gate/run_sprint_on_cloud) after target validation and recovers stale ones.
- Repair/escalation machinery: reads/writes the escalation ledger, needs-human markers, and repair locks before resuming a session; launches fix-the-fixer D10 meta-fixers as durable managed runs.
- Managed-agent module: shares the neutral arnold-managed-agent-run-v2 manifest lifecycle and custodian with the watchdog/repair stack so resident-delegated and machine-repair agents use one evidence/lineage format.
- Provider runtimes: hermes / codex exec / claude backends normalized by provider_runtime.py; key pool resolves provider-prefixed models.
- Schedule repository: append-only JSON store (definitions/heads/occurrences/occurrence-events) guarded by a process-wide flock; also consumed by watchdog/superfixer (sched_superfixer_status_<session> schedules).
- Initiative/editorial layers: create/read/write epics, sprints, checklists, and .megaplan/initiatives/<slug> docs under the layout policy; search before create.
- Timezone service + knowledge lifecycle: IANA preference resolution; document→ticket→initiative promotion rules surfaced in hot context.

**Invariants:**
- Every eligible inbound message is durably claimed by exactly one turn; duplicates never create a second turn or reply.
- Outbound idempotency: crash-before-outbound may retry; crash-after-outbound never resends; post-send state resumes without another user-facing reply.
- Allowlist authorization for all inbound; admin required for high-impact actions (cloud_start, admin, repo_write, artifact_write, export, archive_logs, reconcile_apply).
- Exact-phrase confirmations (with expiry and durable confirmation jobs) gate high-impact actions; confirmation bound to the requesting subject/user.
- Schedule authorization is immutable: work_intent must not exceed the grant's maximum_work_intent; delivery route must equal the grant's route_ref; prompt bytes must match prompt_digest; expired grants fail at launch.
- No competing workers: occurrence claim uses lease + fence + claim_token; stale claims reclaimed; transitions validated against expected fence/token.
- Concurrency guards: default max_active=1, overlap=forbid; hierarchical quotas (global/principal/custody/model caps); per-schedule/per-group limits; quota_breach suppresses or pauses.
- Fail-closed accounting: cost/token ceilings without an accounting backend dead-letter the occurrence rather than launching unbounded.
- Misfire policy never loses a recurrence silently: latest_once default; suppressed occurrences recorded with a decision; dead-letters recoverable only by replay under a NEW grant.
- Git custody enforcement: git-backed execution must carry verified custody evidence; non-mutating execution must NOT carry git evidence (contract mismatch fails).
- Single synthesis/delivery owner per aggregation key: contributors report through the owner, never emit independent user-facing completions.
- Stale-snapshot honesty: stale canonical snapshot has numbers stripped + verbatim WATCHDOG STALE banner; missing/degraded status is labeled degraded, never silently replaced.
- Repair lock required before escalation resume (no competing fixers); escalation answer must come from the designated responder/channel and must not be stale.
- Delivery in production requires BOTH resident mode=production AND discord_bot_role=production; trusted-container/launch attestation gates resident runtime entry.

### Fixer Stack

**Role:** The cloud repair machinery that keeps every Megaplan chain alive and durably advancing. When a chain fails or stalls it observes, classifies whether the stop is genuinely repairable / human-required / a superfixer bug, then repairs at root: investigate the true cause, apply the smallest safe fix in the approved editable Arnold runtime (never the epic's project tree), and re-drive the chain past its frozen baseline via auto/resume until durable milestone movement is proven. Layered superfixer: 1h watchdog → L1 repair-loop → L2/L3 meta-repair-loop → 6h progress auditor, plus an hourly meta-loop that supervises the superfixer itself.

**How it works:** An escalation ladder with a single shared custody classifier. (1) OBSERVE: the 1h watchdog scans every active cloud session each tick, syncs the editable install, classifies each session (alive+advancing / expected-manual / actively-under-repair / stopped-stalled), writes a fresh watchdog-report.json, and enqueues any unintended nonterminal condition as a repair request. (2) CLASSIFY+DISPATCH: repair-trigger scans the queue, resolves the target, projects repair custody, and runs the canonical shared classifier classify_repair_dispatch; conservative defaults (unknown/ambiguous blocker shapes never auto-dispatch); coalesces duplicates by problem-signature, marks stale requests terminal, acquires a trigger lock, claims a singleton blocker, and background-dispatches repair-loop so a tick never blocks. (3) L1 REPAIR: repair-loop acquires a per-session repair lock (atomic mkdir + owner metadata), tries cheap mechanical repairs (source-initiative, source-workspace, dependency-manifest, stale-state clear, baseline relaunch) each verified by verify_started_and_holding (live_with_fresh_activity); if still stuck, runs up to REPAIR_ITERATION_MAX=3 dev-fix investigate-then-mutate turns with escalating models (glm-5.2 → codex:gpt-5.4 → codex:gpt-5.5), then a Kimi goal-operator launch turn, each followed by mechanical relaunch + verify. Budget capped (REPAIR_BUDGET_SECS=7200). A deterministic-failure breaker escalates to Discord + needs-human when the same signature recurs unchanged. On exhaustion it sends a Discord DM and writes a needs-human marker. (4) L2/L3 META-REPAIR: when one of six triggers matches (repair_timeout, persistent_recurring_retry, state_inspection_failure, model_tool_launch_failure, partial_liveness_recurrence, discord_delivery_failure) the watchdog dispatches meta-repair-loop: recursion guard (max 1/session → durable NEEDS_HUMAN), builds a redacted diagnosis prompt, dispatches Codex as orchestrator (danger-full-access) with DeepSeek/Hermes research subagents for independent root-cause probes, applies a narrow source fix, retriggers ordinary repair, verifies terminal success from an authoritative post-retrigger snapshot, persists a redacted record. (5) 6h PROGRESS AUDITOR: model-judged review of the last 6h per plan; verdicts FIXED <sha>/PASSIVE; an unintended stop with no active/recent repair after ~1h is a superfixer bug → fixes the watchdog/trigger/auditor at source and lets the watchdog relaunch. (6) META-LOOP: hourly durable cron verifies the whole superfixer. Intended unification: one entry seam arnold-repair-loop --mode=reactive|proactive (reactive = on-failure with bounded budget + escalate on uncertainty; proactive = hourly resident schedule with NO-OP guard), internal three-stage pipeline (context swarm of parallel Flash subagents → planning corps producing one plan that durably moves the chain and finds structural issues → Flash executor applying the fix, re-driving, verifying, bounded iterate).

**Interactions:**
- Watchdog → repair-trigger: enqueues repair requests from per-session markers; runs trigger scan each tick; background-dispatches so a tick never blocks.
- Repair-trigger → repair-loop: acquires trigger lock, coalesces by signature, claims blocker (singleton per blocker_id), Popen-dispatches repair-loop with request/blocker env.
- Repair-loop → chain: mechanical relaunch + megaplan auto/resume to re-drive; verify_started_and_holding → live_with_fresh_activity.
- Repair-loop → evidence: writes <session>.repair-data.json, attempts/, index.json, sidecar .repair-progress.json, incident-evidence/; escalation via Discord DM + needs-human marker on exhaustion.
- Watchdog → meta-repair-loop: compute_meta_repair_trigger (six types) → background setsid dispatch; meta-repair → DeepSeek/Hermes subagents via subagent-launcher skill; retrigger_ordinary_repair + verify_retrigger_success (authoritative terminal snapshot gate).
- Progress auditor (6h) → watchdog/trigger/auditor source on editible-install → push → watchdog relaunch (fix the superfixer, not the epic).
- All layers → .megaplan/fixer-sessions/index.md + summaries/ (context swarm reads past failure patterns); fixer → epic/session ticket via synthesis/delivery owner (persists structural/underlying issues); fixer → /workspace/repair-findings/persistent-problems.md.
- Superfixer_episodes → review-gated lessons: immutable failure episodes, allow-listed lessons only after ground-truth recovery + human review.

**Invariants:**
- No competing fixers: repair_lock.py atomic-mkdir lock + owner metadata; inspect detects stale (owner_pid_not_live, owner_process_mismatch, timeout_expired); trigger lock + per-session lock; claim_active_repair_request = one active claim per blocker_id. Intended: mechanical per-chain lease with heartbeat renewal, dead-holder reaper, enqueue-on-standdown, reactive lease priority.
- Evidence-gated recovery: repair_goal freezes an acceptance checkpoint before repair; L2 must independently prove a terminal post-retrigger snapshot — a finalized plan, past-end milestone, or dead worker PID are contradiction evidence, not completion.
- Durable movement bar: success = live_with_fresh_activity / milestone advancing beyond the frozen baseline with matching runtime/request/grant/claim/WBC identities and exactly one terminal notification — never a commit, PID, rebind, or model summary.
- Conservative dispatch: classify_repair_dispatch never auto-dispatches unknown/ambiguous blocker shapes; L1 reserved for blocked/manual_review with implementation-repairable failure kind.
- No meta-repair recursion: check_meta_repair_recursion (max 1 record/session) escalates to NEEDS_HUMAN; unrecordable launch failures do not poison the guard.
- Budget caps: REPAIR_BUDGET_SECS=7200, REPAIR_ITERATION_MAX=3, dev/kimi timeouts, KIMI_MAX_TURNS=40; deterministic-failure breaker stops same-signature retry loops.
- Process custody fail-closed: never signal/kill a process without exact durable launch provenance binding acting-run identity, target managed-run identity, and lifecycle op; no pgrep-derived kill lists.
- Profile integrity: never re-route a phase model/vendor/provider to work around a missing credential; restore config after diagnosis; never leave a profile mutation behind.
- Obvious-fix fast path only when root cause is unambiguous, fix minimal+contained, verifiable with a focused check, and no competing owner/gate blocks; otherwise full investigation loop.
- simple_fixer/superfixer authority derived ONLY from the exact F01 repair-occurrence tuple (never label, liveness, WBC receipt, or rebuildable projection); no-child-agent gate (fixer is a leaf); singleton exact-occurrence claim; durable two-try unchanged-fingerprint mutation budget; action gates at every mutation boundary.
- Effect-class allowlist: unknown/non-idempotent/ambiguous effect classes stay action-off and produce typed escalation; ENGINE_RUNTIME repairs require separate typed admission (Run Authority + Custody + WBC + effect fence).
- Fixer edits the approved editable runtime, never the epic's project tree; fixer pre-flight asserts the edit target is the executed tree (shadow/mount detection, st_dev/st_ino) — a shadowed/inert path is an error, never an edit target.

### Cloud Runtime + Deploy

**Role:** Runs the Megaplan chain/plan/resident/fixer machinery unattended on a remote cloud box (Hetzner agentbox) and keeps the running code recoverable, singular, and inspectable. Its operating model: one thin stable bootstrap Docker image whose operational logic ships through an on-volume Arnold source clone refreshed from the durable origin/editible-install branch; one cloud.yaml per initiative as the deployment manifest; an immutable content-addressed runtime per promoted commit selected by durable selector files; and the cloud watchdog as process supervisor with host systemd ensure-timers as the singleton recovery mechanism (the 'never dark' guarantee).

**How it works:** Providers: local (docker compose) or ssh (Hetzner agentbox; rsync deploy dir, single long-lived container), fly reserved. cloud build docker-builds the thin image (ubuntu 22.04 + pyenv 3.11 + node + bun + codex CLI + claude + arnold[agent] from PyPI); cloud deploy syncs the deploy dir and .env, builds, and launches the container with a persistent volume. On boot the entrypoint ensures the repo checkout, seeds OAuth creds from /workspace/.creds into ephemeral /root, writes /root/.codex/config.toml, installs megaplan via mp_install_megaplan at megaplan.ref, prepares the immutable supervisor runtime (current symlink + last-prepare.json), launches four tmux sessions (heartbeat, watchdog, resident if env present, agent) plus a health server, and writes a cloud-session marker for mode:chain. Boot mode is auto/chain/idle; missing inputs warn-and-drop-to-idle rather than crash. cloud chain / launch-epic is the preferred launch path: canonicalize the epic, validate spec + North Star + human-gate policy, preflight runtime deps, FAIL-CLOSED-sync the local launch HEAD to editible-install, upload spec/ideas/anchors to the derived isolated workspace, seed Codex OAuth, run a remote state-reset check, start the chain in a derived tmux session, write a provider-independent marker (last_chain.json), and verify watchdog tracking + liveness before emitting provenance JSON. Code propagation: the ONLY engine-fix path is push to origin/editible-install; the watchdog fast-forwards /workspace/arnold hourly and apply_install_sync runs pip install -e after branch switches that change deps/entry points; /usr/local/bin wrappers must be re-copied manually after wrapper-changing merges. Scheduler: host systemd timers own the loops (watchdog-ensure 1min heartbeat-staleness-aware, resident-ensure 5min, progress-audit 6h, optional repair-trigger, resident-schedule-runner). The watchdog scans cloud-session markers hourly, treats each as a supervised chain, never disturbs live tmux, invokes Kimi/repair-loop for unintended stops, falls back to a one-shot chain start --one under arnold-supervise, writes watchdog-report.json. Promotion/recovery (post-M11 intended): build an immutable runtime from a reviewed FINAL_SHA (clone + frozen venv + prepared supervisor runtime + tagged image), run an isolated read-only canary, then an atomic selector transaction rewriting the three durable selector surfaces under a host cutover lock with fsync+rename, rebind authoritative chain state + marker to the candidate content_sha256 via chain runtime-rebind (CAS) + runtime_cutover, validate the launch seed, deploy+restart through the systemd ensure units, run production acceptance cycles (0/5/10 min probes), then emit release receipts. Unified-fixer design reframes per-epic runtimes as cheap worktrees off one promoted base with per-runtime runtime-manifest.json as the ONLY execution-source resolution, push-at-creation, continuous transactional promotion (never ahead of origin, import smoke test before atomic FF push), shadow-proofing, and closed-only GC.

**Interactions:**
- Chain runner: cloud chain launches remote chain start --spec in tmux; cloud supervise --chain performs one safe tick (restart dead runner, auto-merge/advance per merge_policy) and refuses on running/complete/human_prerequisite/quality_gate/awaiting_pr_merge/stale_bookkeeping; the cloud-session marker written at launch is what the watchdog scans.
- Custody control plane: chain runtime-rebind and marker runtime_cutover require exact terminal chain state + canonical projection; runtime_provenance receipts + engine_runtime_repair admission bind exact runtime/candidate revision to custody/WBC fences; resident-runtime.env selectors are custody-of-the-executed-tree.
- Resident layer: entrypoint + 5min systemd timer launch and health-check the Discord resident from MEGAPLAN_RUNTIME_SRC + PYTHON + launch seed with attestation required; resident reads canonical cloud-status.json (never SSHes back to its own host); resident-schedule-runner timer materializes due schedules.
- Fixer stack: watchdog (tmux, hourly scan) → repair-trigger → repair-loop (L1) / meta-repair (L2/L3); six-hour auditor escalates only with ARNOLD_AUTONOMY=1 + ARNOLD_AUDIT_AUTOFIX_ENABLED=1 and a true-stall gate; all repair binaries resolve through the canonical base/runtime-manifest; repair_lock/lease is the mechanical coordination fence.
- Cloud runtime itself: the thin image is rebuilt only when the bootstrap changes; everything else propagates via editible-install + pip install -e; systemd ensure-timers own singleton recovery; watchdog is the process supervisor; runtime selectors (.cloud-hot-env, resident-runtime.env, systemd drop-in) name exactly one executed tree+interpreter.
- Evidence + gates: preflight JSON, launch provenance, last_chain.json marker, watchdog-report.json, install_sync.applied ledger events, runtime_identity/runtime_provenance receipts, chain execution_binding (runtime_binding.current_identity.content_sha256), release receipts with checkpoint hashes, M11 workflow-canary admission/verification verdicts, acceptance-cycle probes.

**Invariants:**
- The cloud image is a stable base; operational logic ships through the on-volume source clone refreshed by cloud chain before the driver starts (image rebuilt only when the thin bootstrap changes).
- Editible-install is the ONLY propagation path for cloud engine fixes: push to origin/editible-install → watchdog fast-forwards /workspace/arnold → apply_install_sync re-runs pip install -e; no CI, no image rebuild, no orchestrated rollout.
- Push before live: cloud chain syncs the local launch HEAD to editible-install and FAILS CLOSED on a dirty tree or diverged branch.
- No duplicate owners: entrypoint + systemd ensure units own singleton recovery; do not start a second resident/watchdog/repairer/auditor by hand; ensure-watchdog kills a hung watchdog (heartbeat older than ~130m) and restarts fresh.
- Watchdog is the process supervisor and is NOT destructive: its only mutations are tmux session management and chain start --one; it refuses on running/complete/human_prerequisite/quality_gate/awaiting_pr_merge/stale_bookkeeping and never force-pushes, resets, deletes branches, or patches the active chain's project tree.
- Coordination: repair lock/lease prevents competing fixers; one marker store shared by reactive and proactive flows; slot-first watchdog verifies provider/session consistency and only wakes chains the status shows recoverable.
- Shadow-proof execution source: the tree a fixer edits must be the tree the resident executes (realpath == manifest.runtime_root, st_dev/st_ino match, no RO overlay, writable) — a shadowed/inert path is an error, never an edit target.

- Nothing runs un-pushed: running SHAs must be origin-resolvable (preserve branches/snapshot tags + off-box git bundles as backstop); base never ahead of origin; never amend base history (revert via new commit).
- Nothing is deleted unclosed: GC removes only closed + origin-resolvable runtimes; legacy clones frozen-then-deleted only where origin==local.
- Secrets discipline: secrets named in cloud.yaml are uploaded at deploy and redacted from logs; never put tokens in cloud.yaml or the repo; isolated_chain_runner requires secrets: [].

### Evidence + Gates

**Role:** The proof discipline that turns raw run activity into durable, content-addressed, independently verifiable proof that a plan/milestone/chain is genuinely done — and makes 'done' a claim backed by objective evidence, never by status prose, heartbeat, return code, live PID, commit, 'successful' summary, or model self-report. It is what makes the judgment/labor split safe (a weak model cannot quietly claim completion) and the mechanism that surfaces structural/underlying issues into durable records (tickets, critique ledger, fixer-session index) instead of letting them vanish by paraphrase. Three sub-roles stay separated: GATES decide continuation, EVIDENCE records persist objective facts, VERIFICATION re-derives verdicts from evidence.

**How it works:** An ascending evidence chain from raw run IDs to proof: (1) every run writes an append-only events.ndjson journal (lifecycle, subprocess, LLM calls with provider request_id + token heartbeats, artifact writes, decisions, cost) — seq-monotonic and gap-detectable. (2) Each phase writes a WBC step receipt (prompt_hash_raw + prompt_hash_canonical, model, provider facts, phase metrics). (3) Phase artifacts capture per-stage output (plan_v*.md + meta, critique flags with stable IDs, gate.json + gate_signals, finalize.json task DAG with one sense_check per task, execution batch evidence, validation_*.json, review.json). (4) Review collects objective review_evidence.json (git base/head SHAs, invocation id, execution audit context, diff). (5) At plan level the CompletionVerdict computes a typed verdict from objective providers (phase_coverage, landed_diff, worker_did_work, green_suite, execution_acceptance_contract, review_disposition, declared_noop) so 'done' is a claim the verdict confirms from evidence. (6) At chain level proof-map.json maps each milestone label to a non-empty list of proof artifact paths; completion-manifest.json binds chain/north-star/brief sha256, milestone labels in order, status done, publication evidence, and proof_artifacts (path+sha256 each, existence-verified). (7) Milestones may declare typed conformance gates (kind: final_conformance_gate); the driver runs the validator subprocess (no shell), requires exit 0 plus a valid milestone_validation_receipt.v1 (current sha256 of validator/conformance/traceability files, git head, timestamps), and blocks milestone readiness/auto-merge/completion/advancement on failure; a post-merge final gate recomputes so the accepted receipt names the authoritative merge commit, then appends the receipt to the proof map and emits the manifest. (8) Dependent chains declare chain_completed launch preconditions with require_manifest:true; the driver re-validates all hashes byte-for-byte — a genuinely completed predecessor is invisible to its successor unless the evidence matches. Gates are evidence-aware: the gate reads accumulated critique flags (id, concern, evidence, category, severity, revise summary) plus iteration-pressure/debt signals; the reviser must account for every relevant finding; success criteria (must/should/info) are validated for verifiability at critique and adjudicated at review (only must failures block). Structural issues surface through megaplan ticket new (out-of-scope observations), the critique ledger (occurrences → reconciliation → dispositions → response/non-action → independent outcome with reopen rules), and the meta-evidence stack (watchdog reports → repair-data → progress-auditor reports → fixer-session summaries/index.md, with the gather step being the ceiling on what the judging model can see).

**Interactions:**
- Chain runner feeds plan-level artifacts (finalize.json, execution evidence, review.json) into the milestone completion record; the completion manifest binds them via proof-map.json before a milestone is marked done.
- Gate phase consumes critique flags (with evidence) + iteration pressure + gate signals and emits orchestrator_guidance that routes revise/finalize — the gate is evidence-aware, not a fresh universe per iteration.
- Chain driver invokes the declared conformance-gate validator as a subprocess, validates its receipt (returncode 0 + current content hashes), blocks auto-merge/advancement on failure, and rebinds proof after merge.
- CompletionVerdict / review_evidence compute a typed verdict from objective providers and feed the review prompt; in enforce mode it would refuse the done transition when evidence contradicts the claim.
- Launch preconditions (chain_completed + require_manifest) consume the predecessor completion manifest: chain sha, milestone order, brief/chain/north-star hashes, proof artifact hashes, validation receipts, recorded manifest hash.
- Observability (introspect/trace/doctor) are thin readers over events.ndjson — evidence for diagnosis, never authority.
- Tickets link to epics with resolves_on_complete=true; the planner surfaces open tickets at plan time; epic completion auto-addresses them with a resolution_note.
- Fixer-session summarizer writes git-committed 2-sentence summaries + index.md; new fixer goals are injected with the last 5 summaries labeled 'UNTRUSTED HISTORICAL EVIDENCE — verify against current state'.
- Watchdog → repair-loop (L1) → meta-repair (L2) → progress auditor (L3) form the meta-evidence stack: gather-then-judge, with deterministic reasons[] gating which plans reach the model judge.
- North Star anchor is snapshotted at init and bound (path+sha256) into the completion manifest; decision prompts get full anchor context, review prompts get anchor checks.

**Invariants:**
- Evidence, not status prose: 'Success is evidence, not status prose.' Status/Markdown/timelines/projections explain outcomes but never authorize them. Heartbeat, return code, PID, commit, or self-report is never proof — only canonical chain state showing milestone advancement with matching identities (runtime/request/grant/claim/WBC) is proof.
- Content-addressed binding: evidence is admissible only inside the binding's content-addressed scope; exact-set and absence claims require complete capture; bare exists/contains_text checks are never evidence of a binding relationship; proof-map entries must be path+sha256.
- Semantic completion vs transition authority separated: CompletionSpec/Binding/Verdict defines and evaluates proof obligations; Run Authority + Custody + WBC + acceptance transaction authorize; projections never authorize.
- Non-bearer composite receipts: every composite admission receipt rereads current Run Authority grant/fence and Custody lease/epoch, then checks the exact WBC boundary evidence — a host snapshot is coherent evidence, never positive authority.
- Cumulative finding truth: no finding vanishes by paraphrase; the reviser must record an action or explicit justified non-action for every relevant finding; the gate trusts only current, independently reviewable decisions and cumulative state, not the latest critique wording.
- Deterministic code owns identity, hashes, completeness, freshness, idempotency, persistence, phase transitions; models own semantic judgment — the evaluator is a semantic authority, never a workflow authority.
- Fail-closed gates: conformance gate blocks milestone readiness, auto-merge, milestone completion, and downstream advancement when evidence is missing, red, stale, or bound to different source; launch preconditions fail loud on any path/hash mismatch.
- Milestones with a declared transition cannot skip it, and a validator cannot perform the transition itself; proof that must stay effect-inert and the cutover are different milestones; proof and cutover remain separate.
- No self-hosting trust boundary: a bootstrap cannot use the new gate to authorize implementation of that same gate; trusted external CI and a mechanically independent verifier must attest the exact proposed tree before automatic merge; the post-merge final_conformance_gate rebinds proof to the landed tree.
- Immutable evidence, rebuildable projections: accepted events are idempotent (replay cannot double-append); supersession never deletes evidence; historical artifacts remain preserved and content-addressably reachable.
- No competing authority/ledger: no second evidence registry, verdict type, acceptance authority, scheduler, lease system, effect ledger, durable store, or lifecycle may be introduced; every new writer/reader names its owner and retirement/expiry path.
- Completion candidate outcomes (accepted/blocked/waived) and platform enforcement dispositions (always_hard/production_admission_gate/non_durable_only) stay separate typed registries — never collapsed into one enum.
- Waiver semantics: waiver scope/expiry/authority and transitive taint must survive workflow composition without becoming clean parent acceptance; absence of automatic repair is not evidence that recovery is complete.

## Key invariants the system is SUPPOSED to uphold

- Judgment/labor split and enforced rigor: frontier models plan/critique/gate/review, cheap models do the labor, and the harness enforces every step — a weak model cannot quietly claim completion.
- Deterministic resumability: persisted state (state.json + resume_cursor) lets auto drive unattended and resume re-enter the exact phase; one milestone failing never loses prior milestones' work, and failures halt by default.
- Single-driver, no competing owners, no orphaned work: plan-level locks + custody leases (bounded TTL/epoch) + repair locks/leases (heartbeat, reaper, enqueue-on-standdown) make concurrent or stale-owner action impossible.
- Double-fenced action boundary: every authority-increasing action re-reads current Run Authority grant/fence AND current Custody lease/epoch AND required WBC evidence from durable stores — any stale half rejects; projections/PIDs/markers/liveness never authorize.
- Evidence, not status prose: 'done' is a claim confirmed by content-addressed evidence (events.ndjson → step receipts → proof artifacts → proof map → completion manifest → validation receipts → launch preconditions), never by heartbeat, return code, PID, commit, or model self-report.
- Content-addressed binding and fail-closed gates: proof-map entries are path+sha256; launch preconditions and conformance gates re-validate predecessor manifests byte-for-byte and fail loud on missing/stale/rebound evidence.
- Cumulative finding truth: no finding vanishes by paraphrase; the reviser must account for every relevant critique finding; the gate trusts cumulative, independently reviewable state.
- Bounded retries, never infinite loops: cost cap, review-rework cap, critique-iteration cap, repeated-failure-signature cap, per-milestone retry counters — each bails to a recorded failure with resume_cursor + retry_strategy.
- Evidence-gated, durably-moving repair: success = durable milestone movement beyond the frozen baseline with matching runtime/request/grant/claim/WBC identities and exactly one terminal notification; a repair actor never verifies itself (independent verifier + negative control).
- The fixer edits the approved editable runtime, never the epic's project tree; a shadowed/inert edit target is an error, never a target (realpath/manifest/st_dev/st_ino gate).
- Recoverable singular runtime: editible-install is the ONLY cloud engine-fix propagation path; push-before-live fails closed; nothing runs un-pushed and nothing is deleted unclosed; systemd ensure-timers are the singleton recovery mechanism.
- No self-hosting trust boundary and no competing authority: trusted external CI + independent verifier attest the proposed tree before auto-merge; no second evidence registry/verdict/lease/ledger may be introduced; every new writer names its owner and retirement path.
- Shadow-first enforcement rollout: all new authority (custody gates, CompletionVerdict, controlled writers) starts report_only/shadow and promotes only after machine-verifiable acceptance; production enforcement is never silently enabled.

## Gaps / ambiguities in the intended design

- No operator-facing doc states when to use auto vs resume and how the chain reconciles the two; pipeline-resume.md covers only the cursor contract, and the boundary between auto-driver failure and chain reconciliation is fuzzy in the running code.
- The full chain.yaml spec surface is under-documented: launch_preconditions, prerequisite_policy, validation_policy, review_policy.clean_milestone_pr, anchors, and box additions (successors, fresh_child_admission, operator_pause, require_clean_base) are defined in chain/spec.py and NORTHSTARs, not in megaplan-epic.md; the newer epic-chain verb and chain verify/manifest/override subcommands are absent from operator docs.
- The completion contract (shadow/warn/enforce) and full-suite backstop (off/shadow/enforce) modes are implemented but their operator semantics (when to move shadow→enforce, what blocks) are not documented in a single doc; the CompletionVerdict shadow→warn/enforce migration is unscheduled.
- The 'milestone index' has no standalone durable artifact in the intended design (it is ChainState.current_milestone_index + completed[]), and whether a durable milestone-index file is intended is undocumented.
- Custody scope ambiguity: whether leases are strictly per repair occurrence (F01 identity) or also cover ordinary task/session/plan ownership and delivery is under-specified; who owns the lease sweeper/expirer is not documented; cross-chain custody handoff (transfer/release across chain boundaries) is only sketched.
- The exact read-coherence of the double fence (atomic version-token snapshot vs independent rereads) and the ordering/atomicity of custody epochs vs the coordinator fence are asserted as non-negotiable but lack a concrete implementation contract.
- Custody vocabularies coexist: the authoritative lease/epoch/RepairOccurrence model and the resident's git_custody / managed_child_custody JSONL event model — the NORTHSTAR states one joinable causal history but the mechanical join is not fully specified.
- Resident: the migration path for legacy ScheduledJobWorker job types (cloud_check, deferred_turn, heartbeat, confirmation_expiry) to rich ScheduleDefinitions is undocumented; the human grant-issuance flow producing an AuthorizationGrant is not a documented runnable process; multi-worker schedule support is explicitly not enabled; delivery-production policy (which deliveries require production+production-role vs always-deliver) is not fully documented.
- Fixer: the proactive (hourly) flow has no escalation to L2/L3; planning-corps model choice (DeepSeek Flash vs stronger planner) is an open question; real latency/budget targets for reactive vs proactive modes are undefined; the promotion-adjudication rule for conflicting durable fixes from two epics is unspecified; whether box trees actually wire repair_lock.py and share one marker store is unverified.

## Briefing key points

- Two-tier rigor via the judgment/labor split: frontier models decide (plan/critique/gate/review), cheap models do high-volume labor (prep, critique lenses, execution batches), and the harness enforces every step — no phase is left to model volition.
- Sizing: ~2-week plans with three dials at init (profile / robustness / depth); the brief is snapshotted and later edits are not re-read; bigger work = an epic decomposed into milestone briefs + a chain.yaml spec, driven as an ordered chain of milestone plans.
- Phase ladder with require_state guards: prep→plan→critique→gate→revise→finalize→execute→review→done, critique→revise loop re-entering at critique, gate routes PROCEED/ITERATE/ESCALATE/TIEBREAKER. auto = the intentionally-dumb unattended drive loop; resume = single-step recovery re-entering the exact persisted resume_cursor phase; failures halt by default and never lose prior milestones' work.
- The cloud runtime is a thin stable base image; ALL engine fixes propagate through the single durable origin/editible-install branch (watchdog fast-forward + pip install -e) — no CI, no image rebuild, no orchestrated rollout; cloud chain syncs the launch HEAD to editible-install and FAILS CLOSED on a dirty/diverged tree; push-before-live, nothing runs un-pushed, nothing is deleted unclosed.
- The resident is the always-on human interface (converse, schedule, delegate, deliver) — NOT the chain runner, watchdog, or deploy machinery. Every eligible Discord message maps to exactly one durable turn; the schedule layer uses immutable authorization grants + occurrence leases + hierarchical concurrency admission (max_active=1 default); managed subagents carry content-addressed manifests + git-custody evidence and synthesize through one delivery owner.
- The fixer stack is a layered escalation: 1h watchdog observes/classifies → repair-trigger claims a singleton blocker under a conservative shared classifier → L1 repair-loop (mechanical-first, budget-capped, investigate-mutate) re-drives via auto/resume → L2/L3 meta-repair fixes the fixer at source → 6h progress auditor judges the superfixer → hourly meta-loop. Core qualities: no competing fixers (mechanical lock/lease), evidence-gated recovery (durable movement, never a commit/PID/liveness), structural issues surfaced to the ticket.
- Custody is the exclusivity substrate under every action boundary: exact content-addressed action-target identity (F01 tuple), bounded-epoch leases, and a double-fenced action gate that re-reads Run Authority grant/fence + Custody lease/epoch + WBC evidence from durable stores at every dispatch/repair/completion/publication/delivery — any stale half rejects; projections never authorize.
- Evidence not status prose: 'done' is a claim confirmed by an ascending content-addressed chain — run IDs → events.ndjson → WBC step receipts + phase artifacts → review evidence → proof-map.json → completion-manifest.json → validation receipts → launch preconditions; heartbeat, return code, PID, commit, or model self-report is never proof.
- Content-addressed binding everywhere: proof-map entries are path+sha256; conformance gates block milestone readiness/auto-merge/completion/advancement on missing/stale/rebound evidence; chain_completed+require_manifest launch preconditions re-validate the predecessor manifest byte-for-byte before a successor initializes.
- Structural/underlying issues never vanish by paraphrase: they surface to megaplan tickets, the critique ledger (occurrences→reconciliation→dispositions→independent outcome), and the git-committed fixer-session index; cumulative finding truth binds the reviser and the gate.
- Divergences that must be fixed before convergence: custody enforcement is shadow-only (ARNOLD_M7_ACTION_VALIDATOR_ENFORCEMENT=0); running SHAs exist only on the box and violate 'nothing runs un-pushed'; three live trees + a shadowed -live bind-mount vs one canonical base; editible-install sync is disabled; two fixer flows with prompt-level-only coordination; stale OPENROUTER_API_KEY routing alias; box GLM model overrides; scheduler timer fails every minute.
- Shadow-first rollout for all new enforcement: custody gates, CompletionVerdict, and controlled writers start report_only/shadow and promote only after machine-verifiable acceptance; never enable production enforcement silently. No self-hosting trust boundary: trusted external CI + an independent verifier attest the exact proposed tree before auto-merge, and the post-merge final_conformance_gate rebinds proof to the landed tree.
